21. Explain the fundamentals of prompt engineering. Discuss the key components of an effective prompt with suitable examples for each component.

Prompt engineering is the practice of designing and refining the input (prompt) to an LLM so that it reliably produces accurate, relevant and well-formatted output, without changing the model's weights. Because model behaviour is very sensitive to how a task is phrased, a good prompt is a cheap alternative to fine-tuning.

In plain words: an LLM is a very capable but very literal new employee. The clearer your instruction, context, example and format, the better and more consistent the work; vague instructions get vague results.

Key components of an effective prompt

ComponentPurposeExample
InstructionThe task to perform“Summarise the following article in three bullet points.”
ContextBackground the model needsThe article text, or domain background
Input dataThe specific item to work onThe customer review to classify
Output formatStructure of the response“Respond only in JSON with keys sentiment and confidence.”
ExamplesDemonstrations of correct behaviour (few-shot, Q22)Two reviews with their correct labels
Role / constraintsTone, persona, length limits“Answer as a friendly support agent in under 50 words.”

A complete prompt

Role:        You are a customer-support analyst.
Task:        Classify the sentiment of the review below.
Context:     Reviews are for a food-delivery app.
Format:      Reply in JSON: {"sentiment": "Positive|Negative|Neutral", "confidence": 0-1}
Example:     "Great and fast!"  ->  {"sentiment": "Positive", "confidence": 0.95}
Review:      "The food was cold and the service was slow."

Good-practice rules

  • Be specific about audience, length and format — “Summarise this” is weaker than “Summarise for B.Tech students in 150 words”.
  • Use delimiters (quotes, ###, XML-like tags) to separate instructions from input data.
  • Say what to do rather than only what not to do; break complex tasks into steps (Q23, Q27).
  • Iterate: test, look at failures and refine (Q28).

The temperature parameter

Output randomness is controlled by the sampling temperature \(T\), applied to the logits \(z_i\):

\[P(w_i)=\frac{e^{z_i/T}}{\sum_j e^{z_j/T}}\]

Low \(T\) (near 0) makes output focused and repeatable (extraction, classification); high \(T\) makes it more varied (creative writing).

Why it matters: a well-structured prompt reduces ambiguity and hallucination and gives consistent output across calls — often replacing costly fine-tuning.

22. Differentiate between zero-shot, one-shot, and few-shot prompting techniques. Illustrate each technique with an example prompt and discuss scenarios where each is most effective.

These techniques differ only in how many demonstrations are placed in the prompt. The model is never retrained: it learns the task from the prompt itself, which is called in-context learning.

\[\hat y=\arg\max_y\ P_\theta\bigl(y\mid \underbrace{(x_1,y_1),\dots,(x_k,y_k)}_{k\text{ demonstrations}},\ x\bigr),\qquad k=0\ (\text{zero}),\ 1\ (\text{one}),\ 2\text{–}10\ (\text{few})\]

Zero-shot

Only an instruction; the model uses what it learned in pre-training.

Classify the sentiment as Positive or Negative:
"The food was cold and the service was slow."

Best for: simple, common tasks (basic sentiment, translation of common languages, short factual questions).

One-shot

One input–output example shows the expected behaviour and format.

Review: "Amazing product, highly recommend!"  -> Positive
Review: "The food was cold and the service was slow."  -> ?

Best for: when the output format is slightly unusual but one example makes it clear.

Few-shot

Several examples (typically 2–10) covering the different cases.

Review: "Amazing product!"             -> Positive
Review: "Terrible, broke in a day."    -> Negative
Review: "It's okay, does the job."     -> Neutral
Review: "The food was cold and the service was slow." -> ?

Best for: several categories or edge cases (note the Neutral class here), domain-specific labels, strict formatting, and consistency over many queries.

Comparison

Zero-shotOne-shotFew-shot
Demonstrations012–10
Task signalInstruction onlyInstruction + 1 patternInstruction + several patterns
Prompt length / costShortestLongerLongest (more tokens, higher latency)
Consistency of outputLowestBetterBest
RiskWrong format or interpretationCopies the single example too closelySensitive to example choice, order and label balance

Practical tips

  • Choose examples that are diverse, correct and similar to the real input; keep label proportions balanced, since the model tends to over-predict the most frequent or last label.
  • All demonstrations and the query must fit in the context window (Q26).
  • If few-shot is still unreliable for a complex reasoning task, add reasoning steps (Chain-of-Thought, Q23) or fine-tune (Q41).

In plain words: zero-shot is telling an intern “sort these emails by urgency”; one-shot is showing one worked example; few-shot is showing a handful covering different cases.

23. Explain Chain-of-Thought (CoT) reasoning in Large Language Models. Demonstrate, with an example, how CoT prompting improves performance on multi-step reasoning tasks.

What is Chain-of-Thought Reasoning?

Chain-of-Thought (CoT) prompting is a technique where an LLM is prompted (either through instruction or via few-shot examples) to generate intermediate reasoning steps before producing a final answer, instead of jumping straight to the answer. Rather than mapping the question directly to the answer, the model is guided to "think out loud," breaking a complex problem into a sequence of smaller, simpler sub-steps — similar to how a student shows their working on a math exam rather than writing only the final number.

Why It Works

  • LLMs generate text autoregressively — each token is conditioned on everything generated before it. By first generating reasoning steps, the model conditions its final answer on its own intermediate deductions, which sharply reduces errors on tasks that require multiple logical or arithmetic steps.
  • Without CoT, the model must implicitly perform all reasoning "in one shot" within a single forward pass to the answer token — which fails on anything beyond fairly simple problems.
  • CoT emerges as a capability mainly in sufficiently large models — it is considered an emergent ability that appears once model scale crosses a certain threshold.

Example — Standard Prompting vs CoT Prompting

Problem: "Roger has 5 tennis balls. He buys 2 more cans of tennis balls. Each can has 3 tennis balls. How many tennis balls does he have now?"

Standard prompting (direct answer):
Q: Roger has 5 tennis balls. He buys 2 more cans of tennis balls. Each can has 3 tennis balls. How many does he have now?
A: 11

Without shown reasoning, the model has a much higher chance of making an arithmetic slip on multi-step problems, especially as the number of steps grows.

Chain-of-Thought prompting:
Q: Roger has 5 tennis balls. He buys 2 more cans of tennis balls. Each can has 3 tennis balls. How many does he have now?
A: Roger started with 5 balls. 2 cans of 3 tennis balls each is 2 × 3 = 6 tennis balls. 5 + 6 = 11. The answer is 11.

By explicitly writing out "2 cans × 3 balls = 6" and then "5 + 6 = 11" as separate steps, the model is far less likely to skip or miscombine a step — each intermediate result is grounded in the text before the final answer is produced.

Where CoT Helps Most

Task TypeExample
Arithmetic reasoningMulti-step word problems (as above)
Commonsense reasoning"If it's raining and John forgot his umbrella, what should he do?"
Symbolic reasoningTracking state across a sequence of operations (e.g. last-letter concatenation)
Multi-hop question answeringQuestions requiring combining facts from multiple sources

Prompting Variants

  • Few-shot CoT: the prompt includes a few worked examples showing step-by-step reasoning before the actual question.
  • Zero-shot CoT: simply appending a phrase like "Let's think step by step" to the prompt, without any worked examples, has been shown to reliably trigger step-by-step reasoning in large models.

Key takeaway: CoT doesn't add any new knowledge to the model — it restructures how the model uses its existing knowledge, giving it "room to think" across multiple generation steps instead of forcing a single leap to the answer.

24. Explain the concept of self-consistency prompting. Describe how it can be combined with Chain-of-Thought reasoning to improve the reliability of LLM outputs.

The Problem with a Single CoT Path

Even with Chain-of-Thought prompting, an LLM generates text via sampling — a single reasoning path can go wrong at any step (a slip in arithmetic, a wrong logical branch), and that one flawed path is all a standard CoT approach relies on to reach its final answer. There's no way to check the answer against alternative ways of solving the same problem.

What is Self-Consistency?

Self-consistency is a decoding strategy that addresses this by generating multiple independent reasoning paths for the same question (by sampling with temperature > 0 rather than always taking the single most likely path), extracting the final answer from each path, and then selecting the answer that occurs most frequently across all the sampled paths — essentially a majority vote over diverse chains of thought.

Fig 12.1 — Self-consistency: sample several CoT reasoning paths for the same question, then take a majority vote over their final answers

How It Combines with Chain-of-Thought

  1. Prompt with CoT: Use a CoT prompt (few-shot or "let's think step by step") so the model produces explicit reasoning steps, not just a direct answer.
  2. Sample multiple times: Instead of greedy decoding (always picking the highest-probability next token), sample the model's output several times (e.g. 10–40 times) with a non-zero temperature, so each run can take a genuinely different reasoning path.
  3. Extract final answers: Parse out just the final answer from each of the generated reasoning chains, discarding the reasoning text itself at this stage.
  4. Marginalize via majority vote: Select the answer that appears most often across all sampled paths as the final output. Paths that reach the same correct answer via different routes reinforce each other, while a single flawed path gets outvoted.

Why This Improves Reliability

  • Error cancellation: If a mistake in one reasoning path is essentially "random noise," it's unlikely that the same mistake recurs identically across many independently sampled paths — so the correct, more common answer dominates the vote.
  • Captures problem diversity: Many reasoning problems can be solved via multiple valid approaches; sampling diverse paths mirrors how a human might double-check an answer using a different method.
  • No extra training required: Self-consistency is purely a decoding-time strategy — it requires no fine-tuning, just multiple forward passes at inference time.
  • Confidence signal: The proportion of paths agreeing on the majority answer can itself be used as a rough confidence estimate for the final output.

Trade-off: Self-consistency multiplies inference cost by the number of sampled paths (e.g. 20–40× more generation calls), so it's typically reserved for cases where correctness matters more than latency or cost — such as exam-style reasoning benchmarks or high-stakes decision support, rather than every everyday chatbot query.

25. Discuss techniques for generating structured outputs (such as JSON) from LLMs. Explain how function calling can be used to integrate LLM outputs with external tools and APIs.

Applications need output that code can parse, not free-form prose. Structured output (usually JSON) makes the LLM a reliable component of a software system. Function calling then lets it use external tools and data.

Techniques for structured output

TechniqueHow it worksReliability
Prompt-based formattingInstruct “respond only with valid JSON matching this schema”, optionally with a few-shot example.Good, but can still add text or break the syntax
JSON mode / schema-constrained decodingThe API restricts the tokens the model may produce so that the output always matches the schema.Guarantees valid structure
Grammar-constrained generationA formal (context-free) grammar defines allowed output, e.g. any JSON, SQL or a custom format.Guarantees conformance to the grammar
Validate and retryParse the output (e.g. with a Pydantic model); if invalid, send the error back and ask the model to fix it.Good safety net

Constrained decoding works by masking the logits: at each step the probability of any token that would make the output invalid is set to zero and the rest are renormalised,

\[P'(x_t\mid x_{<t})\ \propto\ P(x_t\mid x_{<t})\cdot\mathbf 1\bigl[x_t\text{ keeps the output valid}\bigr]\]

Function calling (tool use)

The developer describes each available function by a name, a description and a parameter schema. When the model decides that the request needs an outside capability (live weather, a database, sending an email), it does not guess; it outputs a structured request naming the function and its arguments. The application runs it and returns the result to the model.

// function definition given to the model
{"name": "get_weather",
 "description": "Current weather for a city",
 "parameters": {"type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"]}}

// model output for "Will I need an umbrella in Pune?"
{"name": "get_weather", "arguments": {"city": "Pune"}}

Workflow

  1. Send the user query together with the tool definitions.
  2. The LLM decides whether a tool is needed and emits a JSON function call.
  3. The application validates the arguments and executes the real function/API.
  4. The result is sent back to the LLM as extra context.
  5. The LLM writes the final, grounded answer.

In plain words: the LLM is an office manager who does not know today's weather but knows exactly which colleague to call and what to ask. The model never executes anything itself, so permissions and validation are enforced in your code.

Significance: together these turn an LLM from a text generator into the reasoning layer of larger systems, the basis of agents and tool-augmented applications (Q10, Q29).

26. Explain the principles of context engineering. Discuss strategies for effectively managing the context window of an LLM when handling large or multi-turn inputs.

Context engineering is the process of designing, organising and supplying the right information to an LLM so that it can give accurate, task-specific answers. Prompt engineering asks “what should the model do?”; context engineering asks “what information does the model need?”

AspectPrompt engineeringContext engineering
FocusThe instructionsThe information given to the model
ContentInstructions, constraints, examplesDocuments, conversation history, retrieved data, tool results
GoalGuide behaviourProvide relevant knowledge within a limited window

Principles

  • Provide relevant and sufficient context; remove unnecessary or distracting information.
  • Organise it in a clear structure (labelled sections); define the task and expected output.
  • Keep the context consistent (no contradictory facts); include constraints and examples where useful.

Example: “Summarise this paper” fails because the model does not know the audience, length or focus. Adding Audience: B.Tech AIML; Length: 150 words; Focus: problem, method, findings; Format: bullet points fixes it.

The context window

An LLM can read only a limited number of tokens \(N\) at a time. Everything, including the answer it will write, must fit:

\[n_{\text{system}}+n_{\text{history}}+n_{\text{retrieved}}+n_{\text{query}}+n_{\text{output}}\ \le\ N\]

Long contexts also cost more and are slower, and models tend to use information at the start and end of a long context better than information in the middle (“lost in the middle”).

Strategies for large or multi-turn inputs

StrategyWhat it does
Truncation / sliding windowKeep only the last \(k\) turns; simple, but old facts are lost.
SummarisationReplace old turns by a running summary; keeps key facts in fewer tokens.
Retrieval (RAG)Store documents outside and fetch only the chunks relevant to the current query (Unit IV).
Prioritisation and orderingPut the most important instructions and evidence at the beginning or end; drop low-value text.
Chunking and map-reduceProcess a long document in pieces, then combine the partial results.
Structured memoryKeep short-term memory (recent turns) and long-term memory (facts, preferences in a store) separately.
CompressionRemove boilerplate, deduplicate, use concise formats (e.g. JSON fields instead of prose).

Budgeting: decide in advance how many tokens each part may use (see the bar above) and trim the lowest-value part first.

27. Explain the concept of prompt chaining. Design a prompt chaining workflow for a multi-step task (e.g., research, summarization, and report generation), describing the role of each prompt in the chain. Write the algorithmic steps (pseudocode) for implementing this prompt chaining workflow.

What is Prompt Chaining?

Prompt chaining is a technique where a complex task is broken into a sequence of smaller sub-tasks, each handled by its own prompt. The output of one prompt becomes (part of) the input of the next. Instead of asking the LLM to "research, summarize and write a report" in one giant prompt, we run a pipeline of focused prompts.

Core idea: \( \text{Output}_n = \text{LLM}(\text{Prompt}_n,\ \text{Output}_{n-1}) \) — each step sees only what it needs, which makes it simpler, more accurate and debuggable.

Why Chain Prompts?

  • Better accuracy: one focused instruction per call; the model is not overloaded.
  • Debuggability: you can inspect the intermediate output of every step and fix the exact failing stage.
  • Context control: avoids exceeding the context window by passing only condensed outputs forward.
  • Modularity: a step can be swapped, retried, or given a different model/temperature.
  • Validation gates: checks (format, length, fact-check) can be inserted between steps.

Workflow: Research → Summarize → Report

P1 Plan → P2 Research → P3 Summarize → P4 Outline → P5 Draft Report → P6 Review

StepRole of the promptInputOutput
P1 — PlanDecompose the topic into 4–5 research sub-questionsUser topicList of sub-questions
P2 — ResearchAnswer each sub-question using retrieved documents / search results; extract key facts with sourcesSub-questions + documentsRaw findings with citations
P3 — SummarizeCondense findings into concise bullet-point summaries, removing duplicationRaw findingsPer-question summaries
P4 — OutlineArrange summaries into a logical report structure (intro, sections, conclusion)SummariesStructured outline
P5 — DraftWrite the full report section by section in the required tone and lengthOutline + summariesDraft report
P6 — ReviewCheck consistency, grammar, factual alignment with sources; return the final versionDraft + findingsFinal report

Pseudocode

FUNCTION generate_report(topic):
    // Step 1: Plan
    plan_prompt   = "List 5 research sub-questions about: " + topic
    sub_questions = LLM(plan_prompt)

    // Step 2: Research (loop over each sub-question)
    findings = []
    FOR EACH q IN sub_questions:
        docs     = retrieve_documents(q)            // search / vector DB
        res_prompt = "Using ONLY these docs, answer: " + q + "\n" + docs
        answer   = LLM(res_prompt)
        IF NOT validate(answer):                    // gate: empty / off-topic
            answer = LLM(res_prompt)                // retry once
        findings.APPEND(answer)

    // Step 3: Summarize
    sum_prompt = "Summarize these findings in bullets:\n" + findings
    summary    = LLM(sum_prompt)

    // Step 4: Outline
    outline = LLM("Create a report outline from:\n" + summary)

    // Step 5: Draft
    draft = LLM("Write a full report following outline:\n" + outline
                + "\nUse facts from:\n" + summary)

    // Step 6: Review
    final = LLM("Proofread, fix inconsistencies, keep facts intact:\n" + draft)

    RETURN final
END FUNCTION

Conclusion: Prompt chaining converts one fragile, overloaded prompt into a reliable pipeline of simple, verifiable steps. It is the foundation of agents and frameworks like LangChain (Q2).

28. Discuss prompt evaluation and optimization techniques. Explain the metrics and iterative refinement strategies used to improve prompt performance for a given task.

Prompt evaluation assesses how good a prompt is by analysing the responses it produces. Prompt optimisation modifies the prompt to improve accuracy, consistency and relevance. The goal is to improve accuracy, reduce ambiguity and hallucination, increase consistency and cut irrelevant output.

Evaluation criteria

CriterionQuestion asked
AccuracyIs the answer factually correct?
RelevanceDoes it address the task?
ClarityIs it easy to understand?
CompletenessDoes it contain everything required?
ConsistencyIs quality similar across repeated runs?
Format complianceDoes it follow the requested structure?

Metrics

Run each candidate prompt on the same fixed test set of \(N\) inputs and compute:

\[\text{Accuracy}=\frac{\#\text{correct}}{N},\qquad \text{Format rate}=\frac{\#\text{valid-format outputs}}{N},\qquad F_1=\frac{2PR}{P+R}\]
  • Consistency: run the same input \(k\) times at temperature > 0 and measure the fraction of runs that agree with the majority answer.
  • Text-overlap metrics (BLEU, ROUGE, BERTScore) when reference answers exist (Q46).
  • LLM-as-a-judge / human rating on a 1–5 scale for open-ended output.
  • Operational: token count, latency and cost per request.

Iterative refinement

TechniqueExample
Add constraintsAudience, length, format, focus (“150 words, bullet points”)
Add examples (few-shot)Show correct input–output pairs for the failing cases
Ask for reasoning“Think step by step” (Q23); self-consistency (Q24)
Use delimiters / structureSeparate instructions from data
Tune decodingLower temperature for consistency
A/B testingCompare two prompt versions on the same set; keep the better one

Before/after example: “Summarise this research paper.” (no audience, length or focus) becomes “Summarise this paper for B.Tech AIML students in 150 words: research problem, methodology, key findings; simple language, bullet points.” — scored on the six criteria above, the second prompt wins on relevance, completeness and format.

Good practice: change one thing at a time, keep a version history of prompts and a fixed regression test set, and re-test when the model is updated.

29. Explain the role of LLM APIs and integration frameworks (such as LangChain) in building intelligent applications. Describe, with a diagram, the architecture of a typical LLM-powered application.

Role of LLM APIs

An LLM API (OpenAI, Anthropic Claude, Google Gemini, Cohere, etc.) exposes a hosted model over HTTP so applications can use it without training or hosting it. The developer sends a request (messages, parameters) and receives generated text, embeddings or tool calls.

API FeaturePurpose
Chat / completion endpointSend messages (system, user, assistant) and receive the model's reply
Parameterstemperature (randomness), max_tokens (length), top_p, stop sequences
Embeddings endpointConvert text into vectors for semantic search / RAG
Function / tool callingModel returns structured JSON to call external tools or APIs
StreamingTokens delivered as generated — responsive UIs

Benefits: no GPU infrastructure, instant access to state-of-the-art models, pay-per-token pricing, easy scaling. Challenges: latency, cost, rate limits, data privacy, vendor lock-in.

Role of Integration Frameworks (LangChain, LlamaIndex)

A raw API call only gives text in → text out. Real applications need prompts, memory, retrieval, tools and multi-step logic. LangChain provides these building blocks as reusable, composable components:

LangChain ComponentFunction

Prompt TemplatesReusable parameterised prompts with variables

Architecture of a Typical LLM-Powered Application

Trace of one request through the application

  1. The user asks: “What is the refund window?”
  2. The app turns the question into an embedding and retrieves the top-3 policy passages (retriever).
  3. A prompt template inserts the passages, the chat history from memory and the question into one prompt.
  4. The prompt is sent to the LLM API with chosen parameters (low temperature for factual answers).
  5. An output parser checks and formats the reply; the app returns it and stores the turn in memory.

Pseudo-code of a chain

prompt = Template("Answer using only the context.\nContext: {context}\nQuestion: {question}")
def answer(question):
    docs   = retriever.search(question, k=3)
    text   = prompt.fill(context=join(docs), question=question)
    reply  = llm.generate(text, temperature=0.2, max_tokens=300)
    memory.save(question, reply)
    return parse(reply)

A framework such as LangChain provides ready-made versions of every line here, so the developer composes components instead of writing the plumbing.

Cost estimate (illustrative prices)

API cost per request \(=n_{in}\,p_{in}+n_{out}\,p_{out}\). With 1,500 input tokens at an assumed \$3 per million and 500 output tokens at an assumed \$15 per million: \(1500\times\frac{3}{10^6}+500\times\frac{15}{10^6}=0.0045+0.0075=\$0.012\). At 10,000 requests a day this is about \$120 per day — which is why prompt length, caching and model choice matter in design.

Fig: Layered architecture of an LLM-powered application

Request Flow

  1. User submits a query through the UI.
  2. Backend passes it to the orchestration layer, which loads memory and fills a prompt template.
  3. If needed, retriever fetches context from the vector DB, or an agent calls an external tool.
  4. The full prompt is sent to the LLM API; the response is parsed and validated (guardrails).
  5. The final answer is returned to the user and the interaction is stored in memory/logs.

Conclusion: APIs give the intelligence; frameworks like LangChain give the plumbing — memory, retrieval, tools and chaining — turning a raw model into a complete, production-ready application.

30. Design the architecture for a conversational AI system using an LLM API. Discuss how the same underlying techniques can be extended to build intelligent content generation and information extraction applications.

A conversational AI system uses an LLM to talk with users in natural language across several turns. Its reliability comes from the software around the model, not from the model alone.

Components

Language understandingInterprets the request (intent, entities); may be done by the LLM itself

Workflow (one turn)

history = [system_prompt]
loop:
    user_msg = receive()
    context  = select(history, user_msg)        # recent turns + summary + retrieved facts
    prompt   = build_prompt(context, user_msg)
    reply    = llm_api(prompt)                  # may call tools and loop

Memory design: buffer (all turns), window (last \(k\) turns) or summary (compressed older turns), chosen by the context-window budget (Q26).

Key challenges

  • Hallucination, context management over many turns, consistency of answers.
  • Privacy of the sensitive information users share; latency for real-time chat; ambiguous or incomplete questions.

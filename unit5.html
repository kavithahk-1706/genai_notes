41. Explain the fundamentals of fine-tuning Large Language Models. Discuss the scenarios in which fine-tuning is preferred over prompt engineering or RAG-based approaches.

What is Fine-Tuning?

Fine-tuning continues training a pre-trained LLM on a smaller, task- or domain-specific dataset so its weights are updated and it learns new behaviour, style or knowledge. It is a form of transfer learning: general language ability from pre-training + specialised skill from fine-tuning.

Pre-training (huge raw text) → Supervised Fine-Tuning (SFT) → Alignment (RLHF / DPO) → Deployed Specialised Model

Fundamentals

Types of Fine-Tuning

TypeDescription
Full fine-tuningUpdates all parameters; best quality, but heavy compute/memory and risk of catastrophic forgetting
Instruction tuning (SFT)Train on (instruction, response) pairs so the model follows instructions
PEFT (LoRA, adapters)Update only a small number of parameters (Q9)
RLHF / DPOAlign the model with human preferences using reward signals / preference pairs

Training Objective

Minimise the next-token cross-entropy loss over the task dataset \(\mathcal{D}\):

\[ \mathcal{L}(\theta) = -\frac{1}{N}\sum_{i=1}^{N}\sum_{t=1}^{T_i} \log P_\theta\big(y_t^{(i)} \mid x^{(i)}, y_{<t}^{(i)}\big) \qquad \theta \leftarrow \theta - \eta\,\nabla_\theta \mathcal{L} \]

Fine-Tuning Workflow

  1. Define task and success metrics.
  2. Collect and clean data — high-quality input/output pairs (quality > quantity; often 1K–100K examples).
  3. Format data (prompt–completion / chat format) and split into train/validation/test.
  4. Choose base model and method (full / LoRA).
  5. Train with a small learning rate (e.g., \(10^{-5}\)–\(10^{-4}\)), few epochs, monitor validation loss to avoid overfitting.
  6. Evaluate on held-out data and safety tests; deploy and monitor.

Fine-Tuning vs Prompt Engineering vs RAG

AspectPrompt EngineeringRAGFine-Tuning
Changes model weights?NoNoYes
Best forQuick tasks, formattingFresh / private factual knowledgeStyle, behaviour, domain skill
Setup costVery lowMedium (pipeline + index)High (data + GPUs)
Updating knowledgeEdit promptInstant (re-index)Retrain
Inference costLong prompts cost moreRetrieval + longer contextShort prompts, lower latency
CitationsNoYesNo

When Fine-Tuning Is Preferred

  • Consistent style, tone or format that prompts cannot reliably enforce (brand voice, strict JSON schema, legal/clinical writing style).
  • Specialised domain language or skills — medical, legal, finance, low-resource languages, code in a proprietary DSL.
  • Complex task behaviour (classification, extraction, reasoning patterns) where many examples teach better than instructions.
  • Reducing cost/latency at scale — a small fine-tuned model replaces a large model with a long few-shot prompt.
  • On-device / private deployment with a compact specialised model.
  • Safety/alignment — teaching refusal behaviours and policy compliance.

Rule of thumb: RAG for knowledge, fine-tuning for behaviour. Start with prompt engineering → add RAG if knowledge is missing → fine-tune if behaviour/style/efficiency is still insufficient. They are often combined (fine-tuned model + RAG).

Risks: catastrophic forgetting, overfitting, data leakage, high cost, and stale knowledge after training.

42. Explain Parameter-Efficient Fine-Tuning (PEFT) and describe the working principle of Low-Rank Adaptation (LoRA), including its mathematical formulation and advantages over full fine-tuning. Write the algorithmic steps (pseudocode) for fine-tuning a pre-trained LLM using LoRA.

Parameter-Efficient Fine-Tuning (PEFT)

Full fine-tuning of a 7B-parameter model needs tens of GB for weights, gradients and optimizer states, and each task needs a complete model copy. PEFT freezes most pre-trained weights and trains only a tiny set of extra or selected parameters (often < 1%), achieving near-full-fine-tuning quality.

PEFT methodIdea
LoRA / QLoRAAdd trainable low-rank matrices to weights (QLoRA: base model quantised to 4-bit)
AdaptersInsert small bottleneck layers between transformer blocks
Prefix / Prompt tuningLearn continuous "soft prompt" vectors prepended to the input
BitFitTrain only bias terms

LoRA — Working Principle

Observation: the weight update \(\Delta W\) during fine-tuning has a low intrinsic rank. So instead of learning the full \(d \times k\) matrix \(\Delta W\), LoRA represents it as the product of two small matrices.

Mathematical Formulation

\[ W' = W_0 + \Delta W = W_0 + \frac{\alpha}{r}\, B A \] \[ W_0 \in \mathbb{R}^{d\times k}\ (\text{frozen}),\quad B \in \mathbb{R}^{d\times r},\quad A \in \mathbb{R}^{r\times k},\quad r \ll \min(d,k) \]

Forward pass for input \(x\):

\[ h = W_0 x + \frac{\alpha}{r} B A x \]
  • \(W_0\): pre-trained weight — frozen (no gradients).
  • \(A\): initialised with small Gaussian values; \(B\): initialised to zero → \(\Delta W = 0\) at start, so training begins exactly from the pre-trained model.
  • \(r\): rank (typically 4–64); \(\alpha\): scaling factor controlling the update's strength.

Fig: LoRA — frozen W₀ in parallel with a trainable low-rank path BA; outputs are summed

Parameter Saving — Example

For \(d = k = 4096\), \(r = 8\):

\[ \text{Full: } d\cdot k = 16{,}777{,}216 \qquad \text{LoRA: } r(d+k) = 8 \times 8192 = 65{,}536 \qquad \Rightarrow\ \approx 0.4\% \text{ of parameters} \]

Advantages over Full Fine-Tuning

AdvantageExplanation
Far fewer trainable parametersTypically 0.1–1% of the model → less memory for gradients and optimizer states
Lower GPU requirement7B–70B models can be tuned on a single GPU, especially with QLoRA
Faster training & cheaperFewer updates per step
Small checkpointsAdapter files are MBs, not GBs — easy to store and share
No inference overheadAfter training, merge: \(W' = W_0 + \frac{\alpha}{r}BA\) → same speed as the base model
Multi-task switchingOne base model + many swappable LoRA adapters (per customer/task)
Less catastrophic forgettingBase weights stay untouched

Pseudocode — Fine-Tuning with LoRA

INPUT : pre-trained model M, dataset D, rank r, scale alpha,
        target_modules (e.g., W_q, W_v), learning rate eta, epochs E
OUTPUT: fine-tuned LoRA adapters (and optionally merged model)

1.  Load pre-trained model M and tokenizer
2.  FREEZE all parameters of M                      // requires_grad = False
3.  FOR EACH target weight W0 (d x k) in target_modules:
        A = random_normal(r, k) * small_std         // trainable
        B = zeros(d, r)                             // trainable, starts at 0
        Replace layer output with:  h = W0*x + (alpha/r) * B*(A*x)
4.  Prepare D: tokenize, format prompt+response, batch it
5.  Initialise optimizer (AdamW) over {A, B} ONLY
6.  FOR epoch = 1 TO E:
        FOR EACH batch (x, y) IN D:
            logits = M(x)                           // forward with LoRA path
            loss   = CrossEntropy(logits, y)
            loss.backward()                         // gradients only for A, B
            optimizer.step();  optimizer.zero_grad()
        Evaluate on validation set; keep best adapters (early stopping)
7.  SAVE adapters {A, B}                            // a few MB
8.  OPTIONAL merge: W0 = W0 + (alpha/r) * B*A       // zero inference overhead
9.  RETURN fine-tuned model

Conclusion: LoRA exploits the low-rank structure of weight updates to deliver full-fine-tuning-like performance with a tiny fraction of the parameters, memory and cost, making LLM customisation practical.

43. Explain the QLoRA technique for fine-tuning Large Language Models. Discuss how it differs from LoRA and the benefits it provides in resource-constrained environments.

QLoRA (Quantised LoRA) combines LoRA with quantisation of the frozen base model. The base weights are stored in 4-bit precision, the small LoRA adapters stay in higher precision and are the only trainable parameters. The result: models that normally need several expensive GPUs can be fine-tuned on a single GPU.

Recall LoRA (Q42)

The pre-trained weight \(W_0\in\mathbb R^{d\times k}\) is frozen and its update is learned as a low-rank product:

\[W=W_0+\Delta W=W_0+\frac{\alpha}{r}BA,\qquad B\in\mathbb R^{d\times r},\ A\in\mathbb R^{r\times k},\ r\ll\min(d,k)\]

Trainable parameters per matrix: \(r(d+k)\) instead of \(dk\). For \(d=k=4096,\ r=8\): \(65\,536\) vs \(16\,777\,216\), i.e. about 0.4%.

What QLoRA adds

  1. 4-bit NormalFloat (NF4) quantisation of \(W_0\). Weights are split into blocks (e.g. 64 values); each block is scaled by its largest absolute value \(c=\max|w|\) and each \(w/c\) is rounded to the nearest of 16 levels. The levels are placed at the quantiles of a normal distribution, because pre-trained weights are roughly normally distributed, so NF4 loses less information than evenly spaced 4-bit levels.
  2. Double quantisation: the per-block scale constants \(c\) are themselves quantised (to 8 bits), saving a further ≈0.4 bit per parameter.
  3. Paged optimisers: optimiser states are moved to CPU memory when the GPU runs out during a memory spike, avoiding out-of-memory crashes.

During the forward pass the 4-bit weights are de-quantised block by block to 16-bit and the adapter is added; gradients flow through the frozen weights to update only \(A\) and \(B\):

\[y=\mathrm{dequant}\bigl(W_0^{NF4}\bigr)\,x+\frac{\alpha}{r}\,B\,(A\,x)\]

Memory arithmetic

Weight memory = number of parameters × bytes per parameter. For 7B parameters: 16-bit = \(7\times10^9\times2=14\) GB; 4-bit = \(7\times10^9\times0.5=3.5\) GB. Full fine-tuning with Adam must also store gradients and optimiser states, about 16 bytes per parameter in total (roughly 112 GB), so it needs a multi-GPU setup.

LoRA vs QLoRA

AspectFull fine-tuningLoRAQLoRA
Base weightsTrainableFrozen, 16-bitFrozen, 4-bit quantised
Trainable parametersAllSmall adaptersSmall adapters
MemoryVery highLowerVery low
HardwareMultiple high-end GPUsOne large GPUOne consumer/mid-range GPU
QualityBest referenceClose to fullClose to LoRA/full on most tasks

Benefits in resource-constrained settings

  • Fine-tune large models (7B–70B) on a single GPU; far lower cost.
  • Adapters are tiny (megabytes), so many task-specific versions can be stored and switched on one base model.
  • Quality close to 16-bit fine-tuning. Trade-off: slightly slower per step because of de-quantisation, and a small accuracy loss from quantisation.

44. Explain the concept of Multimodal AI and Vision-Language Models. Describe, with an example such as CLIP or GPT-4V, how text and image modalities are jointly represented and processed.

Multimodal AI

Multimodal AI systems process and relate multiple types of data (modalities) — text, images, audio, video, sensor data — within one model, as humans do. A Vision-Language Model (VLM) is a multimodal model that understands images and text together, enabling tasks like image captioning, visual question answering (VQA), image–text retrieval, OCR/document understanding and text-to-image generation.

Core Idea: A Shared Representation Space

Each modality has its own encoder, but they are trained so that matching content lands close in a joint embedding space — a photo of a dog and the text "a photo of a dog" have similar vectors.

ModalityEncoderOutput
TextTransformer (tokens → embeddings)Text vector \(\mathbf{t}\)
ImageVision Transformer (ViT) / ResNet — image split into patches (e.g., 16×16) → patch embeddingsImage vector \(\mathbf{v}\)

Example 1: CLIP (Contrastive Language–Image Pre-training)

Fig: CLIP — two encoders trained contrastively into one shared space

Training: for a batch of \(N\) image–text pairs (400M pairs from the web), compute normalised embeddings, all pairwise similarities, and apply a symmetric contrastive (InfoNCE) loss that pulls the \(N\) correct pairs together and pushes the \(N^2-N\) wrong pairs apart:

\[ \mathcal{L} = -\frac{1}{2N}\sum_{i=1}^{N}\left[\log\frac{e^{\,\text{sim}(v_i,t_i)/\tau}}{\sum_{j=1}^{N} e^{\,\text{sim}(v_i,t_j)/\tau}} + \log\frac{e^{\,\text{sim}(t_i,v_i)/\tau}}{\sum_{j=1}^{N} e^{\,\text{sim}(t_i,v_j)/\tau}}\right] \]

where \(\text{sim}\) is cosine similarity and \(\tau\) a learned temperature.

Zero-shot classification: create text prompts "a photo of a {class}" for each label, embed them, embed the image, and pick the label with the highest cosine similarity — no task-specific training required.

Example 2: GPT-4V / Multimodal LLMs

Image → Vision Encoder → Projection to token embeddings → Concatenate with text tokens → LLM Transformer (self-attention) → Text answer

The image is converted into a sequence of "visual tokens" and placed in the same sequence as the text tokens. The LLM's self-attention lets text tokens attend to image patches and vice-versa, so the model can answer, e.g., "What is wrong in this circuit diagram?" or "Describe this chart." This is a fusion architecture, whereas CLIP is a dual-encoder (alignment) architecture.

CLIP vs GPT-4V

AspectCLIPGPT-4V-style VLM
ArchitectureDual encoders, contrastive alignmentVision encoder + LLM, token-level fusion
OutputSimilarity scores / embeddingsFree-form generated text
UseRetrieval, zero-shot classification, guiding diffusionVQA, captioning, reasoning over images

Applications: image search, medical image reports, accessibility (alt-text), document/chart understanding, robotics, autonomous driving, and text-to-image models (CLIP guides Stable Diffusion/DALL·E). Challenges: modality gap, hallucinated visual details, bias from web data, compute cost.

Conclusion: Multimodal models convert images and text into a common vector/token space, so meaning in one modality can be compared with, or reasoned about, in the other.

45. Discuss text-to-image and image-to-text generation techniques. Explain the underlying architectures and provide examples of models used for each task.

Both tasks translate between the language and vision modalities, in opposite directions: text-to-image generates an image from a description; image-to-text generates language from an image.

Text-to-image generation

Input: a prompt such as “a futuristic smart city with autonomous vehicles at sunset”. The prompt is encoded into an embedding, and a generative model creates an image that matches its meaning.

Architecture familyIdeaExamples
GAN-basedConditional GAN with a text embedding (Q15)StackGAN, AttnGAN
AutoregressiveImage as a sequence of discrete tokens predicted by a Transformer given the textDALL·E 1, Parti
Diffusion (dominant)Start from noise and denoise step by step, guided by the text (Q16)DALL·E 2/3, Imagen, Stable Diffusion, Midjourney

In Stable Diffusion (latent diffusion) a VAE compresses the image into a small latent; the U-Net denoises the latent, and the text embedding enters through cross-attention layers; finally the VAE decoder turns the latent into pixels. Text adherence is strengthened by classifier-free guidance:

\[\tilde\epsilon=\epsilon_\theta(x_t,\varnothing)+s\,\bigl(\epsilon_\theta(x_t,c)-\epsilon_\theta(x_t,\varnothing)\bigr)\]

where \(c\) is the text condition, \(\varnothing\) the empty prompt and \(s>1\) the guidance scale (larger \(s\) follows the prompt more strongly but reduces diversity).

Image-to-text generation

Input: an image; output: text. Tasks: image captioning, visual question answering (VQA), image description, document and scene understanding. Typical architecture: a vision encoder extracts visual features, a projection maps them into the language model's space, and a language decoder generates text one token at a time, trained with

\[\mathcal L=-\sum_t\log P_\theta\bigl(w_t\mid w_{<t},\ \text{image}\bigr)\]
ModelDesign
Show-and-TellCNN encoder + LSTM decoder
BLIP, FlamingoViT encoder + Transformer language model with cross-attention
GPT-4V, Gemini, LLaVAVision encoder whose features are projected into an LLM's token space

46. Discuss the evaluation metrics and benchmarking methods used for Large Language Models, including perplexity, BLEU, ROUGE, and standard benchmark suites. Explain the significance of each metric.

Evaluating an LLM is hard because the output is open-ended text; no single number captures quality. Evaluation therefore uses several dimensions — task accuracy, language quality, factuality, reliability and safety/fairness — and several methods: metrics, benchmarks, LLM judges and human raters.

1. Intrinsic metric — perplexity

How well the model predicts held-out text (lower is better):

\[\mathrm{PPL}=\exp\!\Bigl(-\frac1N\sum_{t=1}^{N}\log P_\theta(x_t\mid x_{<t})\Bigr)\]

A model that gives every next word probability \(1/4\) has \(\mathrm{PPL}=4\): it is as uncertain as choosing among 4 equally likely words. It measures fluency/modelling quality, not truthfulness or usefulness.

2. Reference-based text metrics

MetricBasisFormula / ideaTypical use
BLEUn-gram precision\(\mathrm{BLEU}=\mathrm{BP}\cdot\exp\!\bigl(\sum_{n=1}^{N}w_n\log p_n\bigr)\), with brevity penalty \(\mathrm{BP}=\min(1,e^{1-r/c})\) (\(r\)=reference length, \(c\)=candidate length)Machine translation
ROUGEn-gram / LCS recall\(\mathrm{ROUGE\text{-}N}=\dfrac{\#\text{overlapping n-grams}}{\#\text{n-grams in the reference}}\); ROUGE-L uses the longest common subsequenceSummarisation
METEORUnigrams + stems + synonyms\(F_{mean}=\dfrac{10PR}{R+9P}\), score \(=F_{mean}(1-\text{fragmentation penalty})\)Translation
BERTScoreContextual embeddingsMatch each token to its most similar token by cosine similarity, then average to get precision, recall and F1Open-ended generation; recognises paraphrases

Example. Reference: “The cat is sitting on the mat”; generated: “The cat is sitting on a mat”. Six of the seven words match, so unigram precision (BLEU-1 core) \(=6/7=0.86\) and ROUGE-1 recall \(=6/7=0.86\). A paraphrase with the same meaning but different words would score low on both, which is the weakness that BERTScore addresses.

3. Benchmarks

GSM8KGrade-school mathematical reasoning

4. LLM-as-a-judge and human evaluation

  • LLM-as-a-judge: a strong LLM scores answers on criteria (helpfulness, correctness, coherence) or picks the better of two. Scalable and consistent; but biased towards longer answers, towards its own style and towards the answer shown first.
  • Human evaluation: raters score fluency, accuracy, helpfulness, safety, or compare two responses pairwise (win rate). The gold standard for open-ended quality, but slow, costly and subjective.

Benchmarking fairly

Define the goal → choose benchmarks → run all models under the same prompts and settings → compute metrics → analyse failures. Report the methodology and model version; beware of data contamination (the benchmark seen during training); a high score on one benchmark does not imply strength on every task; complement benchmarks with application-specific tests.

47. Explain the fundamentals of LLMOps. Describe the key stages of an LLMOps pipeline, including model deployment, monitoring, and continuous evaluation in production environments.

LLMOps is the set of practices, tools and processes to develop, deploy, monitor, maintain and continuously improve LLM-based applications. Building a demo is only the start; production needs reliable deployment, versioning, monitoring, security and cost control. It extends MLOps with LLM-specific concerns: prompts as code, token-based cost, non-deterministic outputs and hallucination.

Key stages of the pipeline

StageActivities
1. Data preparationCollect, clean and version datasets and knowledge sources (RAG corpora, fine-tuning data)
2. Model developmentChoose the model; engineer prompts; fine-tune with LoRA/QLoRA (Q42, Q43); build RAG; version prompts and models
3. EvaluationOffline tests on a fixed benchmark and regression set; LLM-judge and human review (Q46, Q39); safety tests (Q48)
4. DeploymentPackage and serve behind an API gateway; scale; roll out gradually (canary / A-B) with rollback
5. MonitoringTrack quality, latency, cost, errors, drift and safety incidents in production
6. Feedback & improvementCollect user ratings and failure cases; update prompts, data, retrieval or the model; redeploy

Deployment

OptionUse
Cloud APIHosted model via an API; fastest to start, pay per token
Self-hostedOpen-weight model on private servers; control and privacy
Local / edgeSmall or quantised model on a device; low latency, offline
HybridSensitive requests handled locally, hard ones sent to the cloud

Typical flow: User → API gateway → LLM application → RAG / tools → LLM inference → response.

Inference optimisation

  • Quantisation: memory \(\approx\) parameters × bits/8; a 7B model needs 14 GB in FP16, 7 GB in INT8 and 3.5 GB in INT4, at a possible small quality loss.
  • Batching several requests together raises GPU utilisation and throughput; caching (repeated answers, shared prompt prefixes and the attention KV cache) cuts latency and cost.
  • Compression: pruning, and knowledge distillation, where a small student \(p_s\) learns from a large teacher \(p_t\):
    \[\mathcal L=\alpha\,\mathrm{CE}(y,p_s)+(1-\alpha)\,T^{2}\,\mathrm{KL}\bigl(p_t^{(T)}\,\|\,p_s^{(T)}\bigr)\]

Monitoring and continuous evaluation

What is monitoredMetrics
PerformanceLatency (p50 / p95), throughput (tokens/s), error and timeout rate
CostTokens per request, cost per 1 000 requests, GPU utilisation
QualitySampled LLM-judge scores, faithfulness for RAG, user thumbs-up/down, task success
DriftChanges in user queries, retrieval quality, model or provider updates
Safety and securityPrompt-injection attempts, toxic or leaked content, policy violations

Continuous evaluation re-runs the regression test set whenever a prompt, model or data source changes, uses shadow and canary releases and A/B tests before full rollout, and feeds production failures back into the test set.

Also: version models, prompts and datasets; manage access, secrets and audit logs; control cost with rate limits and budgets.

48. Discuss AI safety and alignment techniques used in Generative AI systems. Explain the role of Reinforcement Learning from Human Feedback (RLHF) and red-teaming in ensuring safe model behaviour.

AI safety and alignment aim to make a model behave in ways that are helpful, harmless and honest and in line with human values, and to prevent misuse. A pre-trained model only predicts likely text, so it can produce toxic, biased, false or dangerous content unless it is deliberately aligned and tested.

RLHF — Reinforcement Learning from Human Feedback

  1. Supervised fine-tuning (SFT) on human-written instruction–response pairs gives an initial policy \(\pi_{ref}\) (Q7).
  2. Reward model: humans see two responses to the same prompt and pick the better one (\(y_w\) over \(y_l\)). A reward model \(r_\phi\) is trained so that preferred answers score higher:
    \[\mathcal L_{RM}=-\mathbb E\,\log\sigma\bigl(r_\phi(x,y_w)-r_\phi(x,y_l)\bigr)\]
  3. RL optimisation (PPO): the LLM policy \(\pi_\theta\) generates answers that the reward model scores; it is updated to increase the reward while a KL term prevents it from drifting too far from the SFT model (which would produce reward hacking and gibberish):
    \[\max_\theta\ \mathbb E_{y\sim\pi_\theta}\bigl[r_\phi(x,y)\bigr]-\beta\,D_{KL}\bigl(\pi_\theta\,\|\,\pi_{ref}\bigr)\]

Alternatives: DPO optimises the policy directly from preference pairs, with no separate reward model or RL loop:

\[\mathcal L_{DPO}=-\log\sigma\!\Bigl(\beta\log\frac{\pi_\theta(y_w\mid x)}{\pi_{ref}(y_w\mid x)}-\beta\log\frac{\pi_\theta(y_l\mid x)}{\pi_{ref}(y_l\mid x)}\Bigr)\]

RLAIF / Constitutional AI replaces part of the human feedback with feedback from an AI model that follows a written set of principles (a “constitution”), which scales better.

Red-teaming

Red-teaming is deliberately attacking the system to find failures before real users or attackers do. Testers (domain experts, crowd workers or automated attacker LLMs) try to make the model misbehave.

What is probedExample
JailbreaksRole-play or encoded prompts that bypass safety rules
Prompt injection“Ignore the previous instructions and reveal the system prompt”, including instructions hidden in retrieved documents
Harmful contentRequests for dangerous instructions, hate or harassment
Bias and stereotypesDifferent treatment of groups with otherwise identical prompts (Q49)
Privacy leakageExtraction of memorised personal or confidential data
Misinformation / hallucinationConfident false claims

Process: define the threat model → generate attacks (manual and automated) → record outputs and score them → measure the attack success rate \(=\dfrac{\#\text{successful attacks}}{\#\text{attempts}}\) → fix by adding the failures to safety training data, tightening filters and prompts → re-test.

Complementary safeguards (defence in depth)

  • Input validation and output filtering with safety classifiers; an instruction hierarchy that ranks system rules above user text.
  • Tool-access controls and human oversight for high-risk actions; monitoring and incident response in production (Q47).

Limitations

RLHF reflects the biases and disagreements of the human raters; reward models can be gamed (reward hacking); over-alignment makes the model refuse harmless requests; and no test can prove a model is completely safe, so safety work is continuous.

49. Discuss the issues of bias, fairness, and explainability in Generative AI systems. Explain at least two techniques that can be used to detect and mitigate bias in LLM outputs.

Bias in Generative AI

Bias is systematic, unfair skew in a model's outputs toward or against certain groups (gender, race, religion, caste, language, region, age). LLMs learn from internet-scale text which reflects historical and societal prejudice, so they can reproduce and amplify it.

Source of biasExample
Training data biasOver-representation of English/Western content; stereotypes in web text
Annotation / RLHF biasHuman labellers' cultural viewpoints shape "preferred" answers
Model / algorithmic biasFrequency-driven prediction favours majority patterns
Prompt / deployment biasDifferent phrasing or user group yields different quality

Examples: "doctor" → assumed male, "nurse" → assumed female; resume-screening favouring certain names; image generators producing only light-skinned CEOs; poorer quality for low-resource languages.

Fairness

Fairness means similar individuals/groups receive similar treatment and outcomes. Common formal definitions (\(A\) = sensitive attribute, \(\hat Y\) = prediction, \(Y\) = true label):

\[ \text{Demographic parity: } P(\hat Y=1\mid A=a) = P(\hat Y=1\mid A=b) \] \[ \text{Equalized odds: } P(\hat Y=1\mid Y=y, A=a) = P(\hat Y=1\mid Y=y, A=b),\ \ y\in\{0,1\} \]

These criteria can conflict with each other and with accuracy, so fairness requires context-specific trade-offs and stakeholder decisions.

Explainability

LLMs are "black boxes" with billions of parameters; it is hard to say why a particular answer was produced. Lack of explainability harms trust, debugging, regulatory compliance (right to explanation in finance/healthcare) and bias auditing.

TechniqueIdea
Attention visualisationShow which tokens the model attended to (partial, not a full explanation)
Feature attribution — LIME, SHAP, Integrated GradientsScore how much each input token contributed to the output
Chain-of-thought / rationalesModel writes its reasoning steps (may not faithfully reflect internal computation)
Citations in RAGGrounds outputs in traceable sources
Model cards / datasheetsDocument data, limitations, intended use

Technique 1: Detecting Bias — Counterfactual / Template Testing

Create paired prompts that differ only in a sensitive attribute and compare outputs:

"He is a software engineer. Describe his strengths."
"She is a software engineer. Describe her strengths."

Measure differences in sentiment, toxicity, word choice, or refusal rates using classifiers. Benchmarks: BBQ, StereoSet, CrowS-Pairs, WinoBias, RealToxicityPrompts. A bias score can be defined as:

\[ \text{Bias score} = \big|\,\mathbb{E}[\text{Sentiment}(\text{output}\mid A=a)] - \mathbb{E}[\text{Sentiment}(\text{output}\mid A=b)]\,\big| \]

A score near 0 indicates fair treatment.

Technique 2: Mitigating Bias — Data Curation & Balancing (pre-processing)

  • Audit the training/fine-tuning data for representation gaps.
  • Counterfactual data augmentation: swap gendered/ethnic terms to create balanced examples ("he" ↔ "she").
  • Re-sample / re-weight under-represented groups; filter toxic content.

Technique 3: Mitigating Bias — Alignment & Prompt-Level Controls (in/post-processing)

  • RLHF / DPO with fairness-aware feedback: reward neutral, inclusive responses; penalise stereotypes.
  • System prompts & guardrails: instruct neutrality; output filters/classifiers for toxic or biased content.
  • Debiased embeddings: remove the "gender direction" from embedding space (projection).
  • Red-teaming & continuous monitoring with diverse reviewers.

Detect (test sets, audits) → Mitigate (data, training, filters) → Re-evaluate → Monitor in production

Conclusion: Bias cannot be eliminated entirely, but it can be measured and reduced. Combining diverse data, counterfactual testing, alignment, guardrails and explainability tools makes GenAI systems more fair, transparent and trustworthy.

2. Privacy Considerations

  • Training data leakage / memorisation: models may regurgitate personal data or secrets seen during training.
  • User data exposure: prompts sent to third-party APIs may contain confidential or personal information.
  • Regulatory compliance: GDPR (EU), India's DPDP Act 2023, HIPAA (health), CCPA — consent, purpose limitation, right to erasure.
  • Mitigations: PII detection and redaction/anonymisation, data minimisation, encryption in transit and at rest, differential privacy during training, federated learning, on-premise / private deployments, retention limits, access control (RBAC) in RAG.
\[ \text{Differential privacy: } \ P[\mathcal{M}(D)\in S] \le e^{\varepsilon}\, P[\mathcal{M}(D')\in S] + \delta \]

Adding or removing one person's record (\(D\) vs \(D'\)) barely changes the output distribution; smaller \(\varepsilon\) = stronger privacy.

1. Explain the evolution of Generative AI from early statistical language models to modern foundation models. Discuss the key differences between traditional AI systems and Generative AI.

Generative AI is the result of about seven decades of progress in modelling the probability of language. Every stage below fixed one weakness of the previous stage.

Stage-by-stage evolution

StageIdeaLimitation that led to the next stage
Statistical (n-gram) models, 1950s–90sCount how often a word follows the previous \(n-1\) words:
\(P(w_t\mid w_{t-n+1:t-1})=\dfrac{\mathrm{count}(w_{t-n+1:t})}{\mathrm{count}(w_{t-n+1:t-1})}\)		Only a short local context; unseen word combinations get probability 0 (data sparsity); no notion of similar words.
Neural language models, 2000sDense word embeddings; RNN/LSTM carry a hidden state: \(P(w_t\mid w_{<t})=\mathrm{softmax}(Wh_t)\)Words must be processed one at a time (slow, not parallel); vanishing gradients for long-range dependencies.

Transformer, 2017Self-attention only, computed for all tokens in parallel (Q3, Q4).Needs huge data and compute — which GPUs/TPUs now provide.

In plain words: early phones remembered only your last word or two (n-gram); RNNs had a short memory; a Transformer can look back at the whole message at once to choose the next word.

The shift is from recognition to creation.

2. Describe the concept of Foundation Models. Explain how they differ from traditional task-specific machine learning models, and discuss their role in enabling Large Language Models.

A foundation model is a very large model, usually a Transformer, pre-trained on broad, internet-scale data with a self-supervised objective, so that one model can serve as the base for many downstream tasks. “Foundation” because many applications are built on top of it, like rooms on a building's foundation.

Self-supervised pre-training objectives

No manual labels are needed: the labels come from the data itself.

\[\mathcal L_{\text{next-token}}=-\sum_{t}\log P_\theta(x_t\mid x_{<t})\qquad\qquad \mathcal L_{\text{masked}}=-\sum_{i\in M}\log P_\theta(x_i\mid x_{\setminus M})\]

The first is used by GPT-style (decoder) models, the second by BERT-style (encoder) models, where \(M\) is the set of masked positions.

Key characteristics

  • Scale: billions of parameters, trained on trillions of tokens.
  • Self-supervision: learns from structure in the data, so unlabelled web text is enough.
  • Emergent abilities: few-shot reasoning, arithmetic and coding appear at sufficient scale without being trained explicitly.
  • Adaptability: same model adapted by prompting, in-context learning, or fine-tuning (Q41).
  • Multimodal versions also exist (CLIP, GPT-4V, Gemini).

Foundation models vs task-specific models

AspectTask-specific modelFoundation model
TrainingFrom scratch for each task on labelled dataPre-trained once on broad data; reused
GeneralisationLimited to the task it was trained forBroad knowledge; transfers to new tasks
CostTraining cost repeated for every taskLarge one-time cost, cheap reuse
DeploymentA new model per applicationOne base + light adaptation
Data needed per taskLarge labelled setFew or zero examples (prompting)

Role in enabling LLMs

An LLM is the foundation model for language. The paradigm “pre-train once at scale, adapt cheaply” is what lets GPT, Claude and Llama do translation, summarisation, coding and chat without a separate model for each. Risks: any bias or error in the foundation model is inherited by every application built on it (homogenisation), and pre-training is very expensive.

3. Explain the Transformer architecture in detail with a neat diagram. Describe the roles of the encoder and decoder stacks, and explain how they interact in encoder-decoder based models.

Why Transformers?

Before Transformers, sequence models like RNNs and LSTMs processed tokens one at a time, which made training slow and made it hard to capture long-range dependencies. The Transformer, introduced in "Attention Is All You Need" (Vaswani et al., 2017), removes recurrence entirely and relies purely on the self-attention mechanism, allowing every token to attend to every other token in parallel.

Overall Architecture

The Transformer follows an encoder–decoder structure. The encoder maps an input sequence into a set of continuous representations; the decoder uses those representations, along with what it has generated so far, to produce the output sequence one token at a time.

Fig 1.1 — Transformer encoder–decoder architecture (Vaswani et al., 2017)

Role of the Encoder Stack

The encoder is a stack of N identical layers (N = 6 in the original paper). Each layer has two sub-layers:

  • Multi-Head Self-Attention: lets every input token look at every other input token and weigh how relevant each one is, producing a context-aware representation for each position.
  • Position-wise Feed-Forward Network: a two-layer fully connected network applied identically to each position, adding non-linearity and representational power.

Each sub-layer is wrapped with a residual connection followed by layer normalization — LayerNorm(x + Sublayer(x)) — which stabilizes training and lets gradients flow through deep stacks. Since attention has no notion of order, positional encodings (sinusoidal functions of position) are added to the input embeddings so the model knows token order.

The output of the encoder is a sequence of contextualized vectors, one per input token, that summarize the entire input in relation to every other token.

Role of the Decoder Stack

The decoder is also a stack of N identical layers, but each layer has three sub-layers:

  • Masked Multi-Head Self-Attention: attends only to earlier positions in the output sequence (future tokens are masked out), preserving the autoregressive property needed for generation.
  • Encoder-Decoder Cross-Attention: the queries come from the decoder, while the keys and values come from the encoder's output. This is exactly where the decoder "looks back" at the input sequence while generating each output token.
  • Feed-Forward Network: same role as in the encoder.

The final decoder output passes through a linear layer and a softmax to produce a probability distribution over the vocabulary for the next token.

How Encoder and Decoder Interact

  1. The encoder processes the full input sequence in parallel and produces a set of key-value pairs representing the input.
  2. The decoder generates output tokens one at a time (autoregressively). At each step, it first attends to the tokens it has already generated (masked self-attention).
  3. It then performs cross-attention against the encoder's output — this is the bridge that lets the decoder condition its generation on the full input sequence, not just what it has produced so far.
  4. This repeats layer by layer, and the final representation is converted into a probability distribution to pick the next token.

Key takeaway: The encoder builds a rich, bidirectional understanding of the input; the decoder generates output autoregressively while continuously consulting the encoder's representation through cross-attention. This division of labor is what makes encoder-decoder Transformers (like the original machine translation model, T5, and BART) effective at sequence-to-sequence tasks.

4. Describe the self-attention and multi-head attention mechanisms used in Transformers. Derive the scaled dot-product attention formula and explain the significance of each term.

Self-attention lets every token build a new, context-aware representation of itself by looking at every other token in the same sequence. Distance does not matter, so long-range dependencies — the weakness of RNNs — are handled directly.

Query, Key, Value

Each input embedding (a row of \(X\)) is projected by three learned matrices:

\[Q=XW^{Q},\qquad K=XW^{K},\qquad V=XW^{V}\]

Think of a library search: the query is what I am looking for, each key labels what a book is about, and the value is the book's content that is returned when the key matches.

Derivation of scaled dot-product attention

  1. Compatibility: the relevance of key \(j\) to query \(i\) is their dot product \(q_i\cdot k_j\). For all pairs at once: the score matrix \(QK^{T}\).
  2. Scaling: if the components of \(q,k\) are independent with mean 0 and variance 1, then \(\mathrm{Var}(q\cdot k)=d_k\). Large scores push softmax into a region with almost zero gradient, so divide by \(\sqrt{d_k}\), which brings the variance back to 1.
  3. Normalisation: softmax turns each row of scores into weights that sum to 1.
  4. Aggregation: the output is the weighted sum of the values.
\[\mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^{T}}{\sqrt{d_k}}\right)V\]

Significance of each term

TermMeaning
\(Q\)what the current token is looking for
\(K\)what each token offers, matched against queries
\(V\)the content that is actually mixed into the output
\(\sqrt{d_k}\)keeps scores in a reasonable range, preventing softmax saturation
softmaxconverts scores into a probability distribution over tokens

Worked example

Let \(d_k=4\) and token 1's scores against two tokens be \(q_1\cdot k_1=2,\ q_1\cdot k_2=1\). Scaled scores: \(2/\sqrt4=1\) and \(1/\sqrt4=0.5\). Softmax: \(e^{1}=2.718,\ e^{0.5}=1.649\), sum \(4.367\), so the weights are \(0.62\) and \(0.38\). The output for token 1 is \(z_1=0.62\,v_1+0.38\,v_2\).

Multi-head attention

Instead of one attention, run \(h\) heads in parallel, each with its own projections into a smaller space (\(d_k=d_{model}/h\)); concatenate and project:

\[\mathrm{head}_i=\mathrm{Attention}(XW_i^{Q},XW_i^{K},XW_i^{V}),\qquad \mathrm{MultiHead}=\mathrm{Concat}(\mathrm{head}_1,\dots,\mathrm{head}_h)\,W^{O}\]

Each head can specialise — one may track subject–verb agreement, another what “it” refers to. In the original Transformer \(d_{model}=512,\ h=8,\ d_k=64\), so the cost is similar to a single full-width head but the model sees several kinds of relationship at once.

5. Explain various tokenization techniques used in Large Language Models such as Byte-Pair Encoding (BPE), WordPiece, and SentencePiece. Illustrate the tokenization process with a suitable example. Write the algorithmic steps (pseudocode) for the Byte-Pair Encoding (BPE) tokenization algorithm.

Why Tokenization Matters

LLMs cannot process raw text directly — text must be broken into discrete units called tokens, each mapped to an integer ID. The choice of tokenization strategy affects vocabulary size, how well the model handles rare/unseen words, and overall model efficiency. Modern LLMs use subword tokenization — a middle ground between word-level (huge vocabulary, can't handle unseen words) and character-level (small vocabulary, very long sequences).

1. Byte Pair Encoding (BPE)

BPE starts with a vocabulary of individual characters and iteratively merges the most frequent adjacent pair of symbols into a new symbol, repeating this a fixed number of times to build up a subword vocabulary. It is used in GPT-2/GPT-3.

Example: Given the word "lower" appearing frequently alongside "lowest" and "newer":

StepActionResult
0Start with charactersl · o · w · e · r
1Most frequent pair: (l, o)lo · w · e · r
2Most frequent pair: (lo, w)low · e · r
3Most frequent pair: (e, r)low · er

After enough merges, "low" and "er" become subword units reused across "lower", "lowest", and "newer", letting the model generalize to unseen combinations like "lowering" → low + er + ing.

2. WordPiece

WordPiece (used in BERT) is similar to BPE in that it also builds a vocabulary via merges, but instead of merging the most frequent pair, it merges the pair that maximizes the likelihood of the training data when added to the vocabulary — i.e. it picks merges that most improve the language model's probability of the corpus, not just raw frequency.

Example: The word "unhappiness" might be split as:

un + ##happi + ##ness

The ## prefix indicates the subword is a continuation of the previous token, not a new word — this lets WordPiece distinguish "happiness" from a token that happens to start with the same letters at the beginning of a word.

3. SentencePiece

SentencePiece is a tokenization framework (used by T5, LLaMA, ALBERT) rather than a single algorithm — it can implement BPE or a unigram language model internally. Its key innovation is that it treats the input as a raw stream of Unicode characters, including whitespace as a regular symbol (often represented as ▁), rather than assuming text is pre-split on spaces.

Example: The sentence "Hello world" tokenizes as:

▁Hello + ▁world

Because whitespace is encoded explicitly, SentencePiece is language-agnostic and works well for languages like Japanese, Telugu, or Chinese that don't use spaces to separate words — this is the main reason multilingual LLMs favor it over BPE/WordPiece.

Comparison

TechniqueMerge CriterionUsed InWhitespace Handling
BPEMost frequent pairGPT-2, GPT-3, RoBERTaPre-tokenized on spaces
WordPieceMaximizes corpus likelihoodBERT, DistilBERTPre-tokenized on spaces
SentencePieceBPE or Unigram LM (configurable)T5, LLaMA, ALBERT, mT5Treats space as a symbol (▁)

Common goal: All three balance vocabulary size against sequence length, and all handle out-of-vocabulary words gracefully by falling back to smaller subword units rather than an <UNK> token.

Algorithm — Byte-Pair Encoding (pseudocode)

Input : corpus, target vocabulary size V
1.  vocab  = all individual characters (or bytes)
2.  split every word into characters + end-of-word marker 
3.  while |vocab| < V:
4.      count every adjacent symbol pair over the whole corpus (weighted by word frequency)
5.      (A, B) = most frequent pair
6.      replace every occurrence of (A, B) by the new symbol AB
7.      vocab = vocab + {AB};  merges.append((A, B))
8.  return vocab, merges

Encoding a new word:
9.  split the word into characters + 
10. for (A, B) in merges (in learned order): merge A B wherever they are adjacent
11. return the resulting tokens

Worked example

Corpus: low×5, lower×2, newest×6, widest×3. Initial pair counts: (e,s)=9, (s,t)=9, (t,</w>)=9, (w,e)=8, (l,o)=7, (o,w)=7. Merges learned (ties broken in order of appearance):

StepMergeCountNew symbol
1e + s9es
2es + t9est
3est + </w>9est</w>
4l + o7lo
5lo + w7low

Encoding the unseen word lowest: l o w e s t </w> → (1) l o w es t → (2) l o w est → (3) l o w est</w> → (4) lo w est</w> → (5) low est</w>. Final tokens: [low, est</w>] — a word never seen in training is built from known pieces.

6. Explain the concept of embeddings and vector representations in NLP. Differentiate between static word embeddings and contextual embeddings, and discuss their role in semantic similarity tasks.

What are Embeddings?

An embedding is a dense, low-dimensional vector representation of a discrete object (a word, subword, or token) such that objects with similar meaning end up close together in vector space. Instead of representing a word as a sparse one-hot vector of vocabulary size, embeddings compress meaning into a continuous space (typically 100–4000 dimensions), where geometric relationships (distance, direction) capture semantic relationships.

Static Word Embeddings

Static embeddings assign one fixed vector per word, regardless of context. Models like Word2Vec (CBOW / Skip-gram) and GloVe learn these vectors from co-occurrence statistics across a large corpus.

  • The word "bank" gets the exact same vector whether it means a riverbank or a financial institution.
  • Famous property: vector arithmetic captures analogies, e.g. vector("King") − vector("Man") + vector("Woman") ≈ vector("Queen").
  • Fast to use (a simple lookup table), but cannot disambiguate polysemous words.

Contextual Embeddings

Contextual embeddings, produced by models like ELMo, BERT, and GPT, generate a different vector for the same word depending on its surrounding context. The embedding is the output of running the full sentence through a deep neural network (typically a Transformer), so it reflects the word's role in that specific sentence.

  • "bank" in "I sat by the river bank" gets a different vector than "bank" in "I deposited money in the bank."
  • Captures syntax, polysemy, and long-range dependencies far better than static embeddings.
  • More computationally expensive — requires a forward pass through the model for every new context.

Comparison

AspectStatic EmbeddingsContextual Embeddings

Role in Semantic Similarity Tasks

Once text is represented as vectors, semantic similarity between two pieces of text is typically measured using cosine similarity:

\[ \text{sim}(\vec{u}, \vec{v}) = \frac{\vec{u} \cdot \vec{v}}{\lVert \vec{u} \rVert \, \lVert \vec{v} \rVert} \]

A value close to 1 means the vectors point in nearly the same direction (highly similar meaning); close to 0 means unrelated; negative means opposite. This underlies applications such as:

  • Semantic search: retrieving documents whose embeddings are closest to a query embedding
  • Duplicate/paraphrase detection: flagging sentence pairs with very high cosine similarity
  • Clustering & recommendation: grouping similar items in embedding space
  • Retrieval-Augmented Generation (RAG): embedding a knowledge base and retrieving relevant chunks for an LLM's context

Key insight: Contextual embeddings from Transformer-based models are now the default for serious semantic-similarity work because a single static vector simply cannot represent a word that means different things in different sentences.

7. Differentiate between pre-training, fine-tuning, and alignment in the development lifecycle of a Large Language Model. Explain how each stage contributes to the final model's capabilities.

A modern LLM is built in three sequential stages. Pre-training gives knowledge, fine-tuning gives skills, alignment gives behaviour. Analogy: general schooling, then job training, then on-the-job mentoring.

1. Pre-training

Trained from scratch on a massive unlabelled corpus (web, books, code) to predict the next token:

\[\max_\theta\ \sum_t \log P_\theta(x_t\mid x_{<t})\]

It needs thousands of GPUs for weeks. The result is a base model: knowledgeable and fluent, but it only continues text; it does not follow instructions.

2. Fine-tuning (supervised, SFT)

Trained further on a much smaller curated set of instruction–response pairs with the same cross-entropy loss, computed on the response tokens \(y\):

\[\mathcal L_{SFT}=-\sum_{t}\log P_\theta(y_t\mid x,\,y_{<t})\]

This teaches the model to follow instructions and use a desired format or domain style. It can be done cheaply with parameter-efficient methods such as LoRA/QLoRA (Q42, Q43).

3. Alignment

Shapes behaviour towards helpful, harmless and honest using human preference data. In RLHF, humans rank pairs of responses (preferred \(y_w\), rejected \(y_l\)); a reward model is trained with

\[\mathcal L_{RM}=-\log\sigma\bigl(r_\phi(x,y_w)-r_\phi(x,y_l)\bigr)\]

and the LLM policy \(\pi_\theta\) is then optimised with RL (e.g. PPO), with a KL penalty that keeps it close to the SFT model \(\pi_{ref}\):

\[\max_\theta\ \mathbb E_{y\sim\pi_\theta}\bigl[r_\phi(x,y)\bigr]-\beta\,D_{KL}\bigl(\pi_\theta\,\|\,\pi_{ref}\bigr)\]

DPO reaches the same goal directly from preference pairs without a separate reward model or RL loop (details in Q48).

Contribution of each stage

StageDataObjectiveWhat the model gains
Pre-trainingTrillions of unlabelled tokensNext-token predictionWorld knowledge, fluency, reasoning foundations
Fine-tuning103–106 curated labelled examplesSupervised cross-entropyTask competence, instruction following, format
AlignmentHuman preference comparisonsReward maximisation / preference lossSafety, honesty, helpfulness

Each stage builds on the previous one: together they turn a raw next-token predictor into a safe, instruction-following assistant.

8. Compare the architectures, capabilities, and intended use cases of popular LLMs such as GPT, Gemini, Claude, Llama, and Mistral. Discuss the significance of open-source LLMs in the Generative AI ecosystem.

All the popular LLMs share the same recipe — a decoder-only Transformer (Q3, Q4) pre-trained at scale and then fine-tuned and aligned (SFT + RLHF/DPO). They differ in scale, training data, safety approach, modalities and, above all, licensing: open weights or closed.

Mixture-of-experts (MoE) in one line

An MoE layer has \(E\) expert feed-forward networks, and a router picks the top-\(k\) for each token:

\[y=\sum_{i\in\mathrm{TopK}}g_i(x)\,E_i(x)\]

Only \(k\) of \(E\) experts run per token, so the model has a large total capacity but a small compute cost per token.

Significance of open-source LLMs

  • Transparency and research: allow study of model internals, interpretability and reproducible results.
  • Customisation and privacy: organisations can fine-tune on sensitive data without sending it to a third party.
  • Cost and control: self-hosting removes per-token fees and gives control over latency and deployment.
  • Democratisation: startups, students and researchers can build without expensive API budgets.
  • Ecosystem: quantised versions, fine-tuned variants and tooling (e.g. Hugging Face) grow around open checkpoints.

Caveat: open weights also mean weaker control over misuse, so safety depends on the deployer.

9. Discuss the applications of Large Language Models in text generation, summarization, translation, question answering, and conversational AI, with suitable examples for each.

1. Text Generation

LLMs generate coherent, contextually relevant text by predicting the next token repeatedly, conditioned on everything generated so far.

Example: Given the prompt "Write a short poem about the monsoon," an LLM produces a fluent, stylistically appropriate poem — used in creative writing tools, marketing copy generation, and code generation (e.g. GitHub Copilot).

2. Summarization

LLMs condense long documents into shorter versions while preserving key information. This can be extractive (selecting important sentences) or abstractive (generating new sentences that paraphrase the content).

Example: Summarizing a 20-page research paper into a 200-word abstract, or condensing a news article into 3 bullet points — used in tools like news aggregators and legal document review.

3. Machine Translation

LLMs trained on multilingual data translate text between languages while preserving meaning, tone, and grammar, often outperforming older statistical machine translation systems because they capture context across the whole sentence rather than translating word by word.

Example: Translating "How are you?" into Telugu ("మీరు ఎలా ఉన్నారు?") while correctly handling grammatical gender and formality — used in tools like Google Translate (which now uses Transformer-based NMT) and real-time multilingual customer support.

4. Question Answering (QA)

LLMs answer natural-language questions either from their own trained knowledge (closed-book QA) or by reading a provided passage/document (open-book / reading-comprehension QA, often combined with retrieval).

Example: A student asks "What is the time complexity of merge sort?" and the model answers "O(n log n)" directly, or — given a textbook PDF — answers "According to Chapter 4, what causes thrashing in an OS?" by extracting the relevant explanation from the document.

5. Conversational AI

LLMs power multi-turn dialogue systems that maintain context across a conversation, adapt tone, and can call external tools — going beyond single-turn Q&A to sustained, coherent interaction.

Example: A chatbot that remembers earlier turns in a conversation ("earlier you said you're a second-year student — here's advice tailored to that"), used in customer support bots, virtual assistants (Siri, Alexa-style agents), and tutoring systems.

This works because all five are the same operation — predict the next token given the context — just with different context. That is why one LLM replaces five older task-specific systems.

Applications combine in real products

A customer-support bot (conversational AI) retrieves the policy passage, answers the question from it, translates the reply into the customer's language and summarises the whole chat for the human agent afterwards — four of the five applications in one workflow.

Common limitation across all five

Fluent output is not the same as correct output: generated text can contain invented facts, summaries can drop or distort details, translations can lose nuance, and chatbots can answer confidently without evidence. High-stakes uses therefore add retrieval (Q31), human review or guardrails.

10. Analyze the current industry use cases and emerging trends in Generative AI and LLMs across domains such as healthcare, education, software development, and customer service. Justify their impact with examples.

1. Healthcare

  • Clinical documentation: LLMs auto-generate doctor's notes from patient-doctor conversations, cutting administrative burden.
  • Diagnostic assistance: Generative models assist radiologists by drafting preliminary findings from medical images, later reviewed by a human.
  • Drug discovery: Generative models propose novel molecular structures with desired properties, accelerating early-stage research.

Impact: Reduces physician burnout from paperwork and speeds up early research timelines — but requires strict human-in-the-loop review given the high stakes of medical errors.

2. Education

  • Personalized tutoring: LLM-based tutors adapt explanations to a student's level and answer follow-up questions in real time.
  • Automated content generation: Generating practice questions, quizzes, and study notes tailored to a syllabus.
  • Accessibility: Real-time summarization and translation of lecture content for students with different needs.

Impact: Democratizes access to one-on-one style tutoring at scale, though it raises concerns about academic integrity and over-reliance on AI-generated answers.

3. Software Development

  • Code generation and completion: Tools like GitHub Copilot suggest entire functions based on natural-language comments or partial code.
  • Automated testing: LLMs generate unit tests and identify edge cases from a function's signature and docstring.
  • Debugging and code review: Models explain stack traces, suggest fixes, and flag code smells during review.

Impact: Measurable productivity gains — studies report developers completing tasks noticeably faster with AI pair-programming, though code quality still needs human review.

4. Customer Service

  • AI chatbots and virtual agents: Handle routine queries (order status, refunds, FAQs) without human intervention.
  • Sentiment-aware routing: Detecting frustrated customers from message tone and escalating to human agents automatically.
  • Agent assist: Real-time suggested responses for human support agents, drafted by an LLM and edited before sending.

Impact: Reduces response time and operating cost significantly for high-volume support, while human agents are freed up for complex, high-empathy cases.

Measuring impact — a worked estimate

A support team receives 10,000 tickets a day, and an LLM assistant fully resolves 40% of them, each taking about 6 minutes of agent time:

\[10\,000\times0.40=4\,000\ \text{tickets},\qquad 4\,000\times6\ \text{min}=24\,000\ \text{min}=400\ \text{agent-hours per day}\]

That is the capacity of about 50 full-time agents (8 h each) redirected to the harder cases. This is the kind of argument used to justify adoption, and it must be weighed against the cost of tokens, supervision and the errors the assistant makes.

Emerging trends

  • Multimodal models that read images, audio and documents as well as text.
  • Agents that plan and call tools to complete multi-step tasks, not just answer.
  • RAG as the standard enterprise pattern for grounding answers in private data (Unit IV).
  • Smaller, domain-specific and on-device models (fine-tuned with LoRA/QLoRA) for privacy and cost.
  • Responsible-AI and LLMOps practices becoming a requirement for production deployments (Unit V).

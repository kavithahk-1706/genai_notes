31. Discuss the major limitations of standalone Large Language Models, including hallucination and knowledge cutoff issues. Explain how Retrieval-Augmented Generation (RAG) addresses these limitations.

Limitations of Standalone LLMs

LimitationExplanation
HallucinationThe model generates fluent but factually wrong or fabricated content (fake citations, invented facts) because it predicts the most probable next token, not the true one.
Knowledge cutoffKnowledge is frozen at the end of training; the model knows nothing about later events, prices, laws or research.
No private / domain dataCannot answer about a company's internal documents, policies or databases it was never trained on.
No source attributionKnowledge is stored implicitly in weights — it cannot cite where an answer came from, hurting trust and auditability.
Limited context windowOnly a fixed number of tokens can be fed in; large corpora cannot be pasted into the prompt.
Costly to updateAdding new knowledge via retraining/fine-tuning is expensive and slow.
Bias & inconsistencyReflects biases of training data and can give different answers to the same question.

What is RAG?

Retrieval-Augmented Generation (RAG) combines an information-retrieval system with an LLM. Instead of relying only on memorised (parametric) knowledge, the system first retrieves relevant documents from an external knowledge base and then supplies them as context so the LLM generates a grounded answer.

\[ P(y \mid x) \;=\; \sum_{d \in \text{Top-}k} P(d \mid x)\; P(y \mid x, d) \]

Here \(x\) is the query, \(d\) a retrieved document, and \(y\) the generated answer — the answer is conditioned on retrieved evidence.

RAG Pipeline

Worked example — the same question with and without RAG

Question: “What is our refund window for orders placed after 1 November 2026?”

Standalone LLMRAG system
Knowledge usedOnly what was in training dataRetrieves the current refund-policy document
Typical answerGuesses a “standard 30 days” (plausible but possibly wrong)“14 days from delivery, per Refund Policy v3, section 2”
Verifiable?No sourceYes — cites the passage
If the policy changesNeeds retrainingUpdate the document; the next answer changes

Parametric vs non-parametric memory

A standalone LLM stores knowledge in its parameters (parametric memory): fixed, hard to inspect and expensive to change. RAG adds an external non-parametric memory (the document store) that can be edited, audited and access-controlled at any time, while the model supplies the language ability.

RAG vs fine-tuning

NeedBetter choice
Fresh or frequently changing factsRAG
Answers with citationsRAG
Private documents with access rulesRAG
A new style, format or behaviourFine-tuning
Both facts and behaviourCombine them

Remaining limits of RAG: if retrieval returns the wrong passage the answer is still wrong, and the model may still ignore the context; hence the evaluation in Q39.

How RAG Solves Each Limitation

LLM LimitationRAG Solution

32. Explain the architecture and workflow of a Retrieval-Augmented Generation (RAG) system with a neat diagram, describing the role of each component from query to response generation. Write the algorithm/pseudocode for the end-to-end RAG pipeline, from query embedding to final response generation.

Retrieval-Augmented Generation (RAG) improves an LLM by retrieving relevant information from an external knowledge source before generating the answer: Query → Retrieve → Augment → Generate. The LLM does not have to memorise everything; it looks up what it needs.

Components and their roles

ComponentRole
Knowledge sourceDocuments, databases, web pages or company data
Document processing and chunkingExtract and clean text; split into smaller meaningful chunks (Q35)
Embedding modelConverts chunks and queries into vectors in the same space (Q33)
Vector databaseStores the vectors with text and metadata; fast similarity search (Q34)
RetrieverFinds the top-\(k\) chunks most similar to the query; may add re-ranking (Q38)
Context augmentationCombines instructions + retrieved chunks + query into one prompt (Q36)
LLMGenerates the final answer using the augmented prompt

Workflow — two phases

  1. Knowledge preparation (before queries): collect documents → chunk → embed → store vectors.
  2. Query processing (at query time): embed the query → similarity search → take top-\(k\) chunks → build the augmented prompt → generate the response.

Retrieval selects the \(k\) chunks with the highest cosine similarity to the query:

\[\mathrm{Top}_k(q)=\operatorname*{arg\,top\text{-}k}_{d_i}\ \frac{e_q\cdot e_{d_i}}{\|e_q\|\,\|e_{d_i}\|}\]

and generation conditions on both the query and the retrieved text. In the original RAG formulation the answer probability marginalises over retrieved documents \(z\):

\[P(y\mid x)\ \approx\ \sum_{z\in\mathrm{Top}_k(x)}p_\eta(z\mid x)\,p_\theta(y\mid x,z)\]

Pseudocode — end-to-end RAG

// Phase 1: indexing (offline)
for each document D in corpus:
    for each chunk c in split(D, size=500, overlap=50):
        v = embed(c)
        index.add(v, text=c, metadata=D.source)

// Phase 2: answering (online)
function answer(query, k = 4):
    q        = embed(query)                  # same embedding model
    chunks   = index.search(q, top_k = k)    # nearest vectors
    context  = join(chunks.text)
    prompt   = "Answer ONLY from the context. If it is not there, say you don't know.\n"
             + "Context:\n" + context + "\nQuestion: " + query
    return LLM(prompt)

Example: “What is the minimum attendance to appear for the semester exam?” — the regulations stored in the vector database are searched, the attendance clause is retrieved, and the LLM answers from that clause instead of from memory.

Why RAG

It reduces hallucination (answers are grounded in evidence), overcomes the knowledge cutoff (update the knowledge base, not the model), gives access to private data, and allows citation of sources (Q31).

33. Explain the concept of embedding models and semantic search. Describe how vector similarity measures (e.g., cosine similarity) are used to retrieve semantically relevant documents.

Embedding Models

An embedding is a dense numerical vector (e.g., 384–3072 dimensions) that represents the meaning of a word, sentence or document. An embedding model (Sentence-BERT, OpenAI text-embedding-3, BGE, E5) maps text into a vector space such that semantically similar texts lie close together.

\[ f_\theta : \text{text} \;\longrightarrow\; \mathbf{v} \in \mathbb{R}^d \]

Example: "car" and "automobile" get nearby vectors, while "car" and "banana" are far apart — even though "car" and "automobile" share no letters.

Keyword Search vs Semantic Search

AspectKeyword (BM25 / TF-IDF)Semantic Search
MatchingExact word overlapMeaning-based, via vector similarity
SynonymsFails ("cheap" vs "affordable")Handles naturally
Typos / paraphraseWeakRobust
Exact IDs / rare termsStrongCan be weaker

Semantic Search Process

Embed all documents → Store in vector DB → Embed query → Compute similarity → Return Top-k

Vector Similarity Measures

1. Cosine Similarity (most common)

Measures the angle between two vectors, ignoring their length. Range \([-1, 1]\); closer to 1 means more similar in meaning.

\[ \cos(\mathbf{q},\mathbf{d}) \;=\; \frac{\mathbf{q}\cdot\mathbf{d}}{\|\mathbf{q}\|\,\|\mathbf{d}\|} \;=\; \frac{\sum_{i=1}^{n} q_i d_i}{\sqrt{\sum_{i=1}^{n} q_i^2}\;\sqrt{\sum_{i=1}^{n} d_i^2}} \]

2. Dot Product

\[ \mathbf{q}\cdot\mathbf{d} = \sum_{i=1}^{n} q_i d_i \]

Equals cosine similarity when vectors are normalised to unit length; faster to compute.

3. Euclidean (L2) Distance

\[ d(\mathbf{q},\mathbf{d}) = \sqrt{\sum_{i=1}^{n} (q_i - d_i)^2} \]

Smaller distance = more similar. Sensitive to vector magnitude.

Worked example — ranking with cosine similarity

Let the query be \(q=(1,2)\) and three documents \(d_1=(2,4)\), \(d_2=(2,1)\), \(d_3=(-2,1)\). Then \(\|q\|=\sqrt5\).

Doc\(q\cdot d\)\(\|d\|\)CosineEuclidean distance
\(d_1\)10\(\sqrt{20}\)\(10/(\sqrt5\sqrt{20})=1.0\)\(\sqrt{1+4}=2.24\)
\(d_2\)4\(\sqrt5\)\(4/5=0.8\)\(\sqrt{1+1}=1.41\)
\(d_3\)0\(\sqrt5\)0.0 (unrelated)\(\sqrt{9+1}=3.16\)

Cosine ranks \(d_1\) first because it points in exactly the same direction as \(q\) (same “topic”, just a longer text), then \(d_2\), then \(d_3\). Euclidean distance would rank \(d_2\) first because \(d_1\) is longer and therefore farther away. For text, direction carries the meaning and length mostly reflects document size, so cosine (or dot product on normalised vectors) is preferred.

Practical points

  • Normalise embeddings to unit length; then dot product equals cosine and is cheapest to compute.
  • Use the same embedding model for documents and queries; vectors from different models are not comparable.
  • Chunk size matters: a vector for a whole book blurs many topics, one for a single sentence may lack context (Q35).
  • For millions of vectors, exact comparison is too slow; approximate search (IVF, HNSW, Q34) is used.

Fig: Small angle (Doc A) → high cosine similarity → semantically close to query. Doc B points elsewhere → irrelevant.

Worked Example

Let \(\mathbf{q}=(1,2)\), \(\mathbf{d_1}=(2,4)\), \(\mathbf{d_2}=(3,-1)\).

\[ \cos(\mathbf{q},\mathbf{d_1}) = \frac{1\cdot2+2\cdot4}{\sqrt5\cdot\sqrt{20}} = \frac{10}{10} = 1 \qquad \cos(\mathbf{q},\mathbf{d_2}) = \frac{1\cdot3+2\cdot(-1)}{\sqrt5\cdot\sqrt{10}} = \frac{1}{7.07} \approx 0.14 \]

\(\mathbf{d_1}\) points in exactly the same direction as the query → retrieved first. \(\mathbf{d_2}\) is nearly unrelated → ranked lower.

Efficient Retrieval at Scale

Exact search over millions of vectors is slow, so vector DBs use Approximate Nearest Neighbour (ANN) indexes — HNSW (graph-based), IVF (clustering), PQ (compression) — trading a tiny accuracy loss for huge speed gains.

Conclusion: Embeddings convert meaning into geometry; cosine similarity converts "is this relevant?" into "is the angle small?". This is the retrieval engine of every RAG system.

34. Discuss the role of vector databases and indexing mechanisms in RAG systems. Explain at least two indexing algorithms (such as HNSW or IVF) used for efficient similarity search.

A vector database stores high-dimensional embedding vectors together with their original text and metadata, and returns the vectors most similar to a query vector. In RAG it holds the chunk embeddings and makes retrieval fast enough for millions of chunks.

Role in RAG

  • Fast similarity search and scalability to millions or billions of vectors.
  • Indexing structures that avoid comparing the query with every vector.
  • Metadata filtering (source, date, category, access rights) and persistent storage.
  • Examples: FAISS, Pinecone, Milvus, Weaviate, Qdrant, Chroma, pgvector.

Why indexing is needed — ANN search

Exact (brute-force) search compares the query with all \(N\) vectors of dimension \(d\): cost \(O(Nd)\). Approximate Nearest Neighbour (ANN) search examines only a promising subset and returns near-optimal neighbours much faster, trading a little recall for large speed-ups.

1. IVF (Inverted File index)

  1. Build: run k-means to partition the vectors into \(n_{list}\) clusters (cells); store each vector in the list of its nearest centroid.
  2. Search: compare the query with the \(n_{list}\) centroids, pick the \(n_{probe}\) closest cells, and scan only the vectors in those cells.

Example: \(N=10^6,\ n_{list}=1000,\ n_{probe}=10\): about \(1000+10\times1000=11\,000\) distance computations instead of \(10^6\), i.e. roughly 90× fewer. A larger \(n_{probe}\) gives higher recall but slower search; neighbours lying just across a cell boundary can be missed.

2. HNSW (Hierarchical Navigable Small World graph)

  1. Build: connect each vector to its nearest neighbours in a graph; vectors are assigned to random maximum layers so the upper layers are sparse “highways” and layer 0 contains all vectors.
  2. Search: start at the entry point in the top layer, move greedily to the neighbour closest to the query until no neighbour is closer, then drop one layer and repeat; at layer 0 explore a candidate list of size \(ef_{search}\) and return the top-\(k\).

Search cost is about \(O(\log N)\). Parameters: \(M\) (neighbours per node), \(ef_{construction}\) and \(ef_{search}\); larger values give higher recall but more memory and time.

Comparison of common indexes

IndexIdeaSpeedRecallMemory
FlatCompare with all vectorsSlow for large \(N\)Exact (100%)Full vectors
IVFCluster, search nearest cellsFastHigh, depends on \(n_{probe}\)Full vectors + centroids
HNSWLayered neighbour graphVery fastVery highHigher (graph links)
Product Quantisation (PQ)Compress each vector into short codesFastLower (lossy)Much smaller

PQ splits a vector into \(m\) sub-vectors and replaces each by the id of its nearest centroid (1 byte each); a 768-dimensional float32 vector (3072 bytes) with \(m=96\) becomes 96 bytes, about 32× smaller. It is often combined with IVF (“IVF-PQ”).

Choice depends on: dataset size, latency requirement, memory budget and required accuracy.

35. Explain various document chunking strategies used in RAG pipelines. Discuss how the choice of chunking strategy affects retrieval quality and downstream generation accuracy.

Why Chunking?

Chunking splits large documents into smaller pieces before embedding. It is needed because (1) embedding models have token limits, (2) one vector for a whole document blurs many topics together, and (3) the LLM context window can only hold a few passages. Each chunk becomes one retrievable unit.

Chunking Strategies

1. Fixed-Size Chunking

Split every N tokens/characters (e.g., 500 tokens). Simple and fast but may cut sentences or ideas in half.

2. Fixed-Size with Overlap (Sliding Window)

Consecutive chunks share some tokens (e.g., 500 size, 50–100 overlap) so context at the boundaries is not lost.

\[ \text{Number of chunks} \approx \left\lceil \frac{L - O}{C - O} \right\rceil \]

\(L\) = document length, \(C\) = chunk size, \(O\) = overlap.

3. Sentence / Paragraph-Based Chunking

Split on natural boundaries (sentences, paragraphs, line breaks) so each chunk is a complete thought.

4. Recursive Character Splitting

Tries separators in order ("\n\n" → "\n" → ". " → " ") until chunks fit the size limit — default in LangChain; preserves structure as far as possible.

5. Structure / Document-Aware Chunking

Uses headings, sections, tables, code blocks, Markdown/HTML tags. Ideal for manuals, legal contracts, and technical docs.

6. Semantic Chunking

Embeds sentences and starts a new chunk when similarity between adjacent sentences drops below a threshold — chunks are topically coherent.

7. Hierarchical / Parent-Child Chunking

Small child chunks are used for precise retrieval; when matched, the larger parent chunk is passed to the LLM for full context.

Practical tuning: typical sizes are 200–1000 tokens with 10–20% overlap; evaluate using retrieval metrics (Recall@k, MRR) and answer-faithfulness on a test question set, then iterate.

Conclusion: Chunking is the silent foundation of RAG — "garbage chunks in, garbage answers out." The right strategy balances context completeness against retrieval precision for the specific document type.

36. Explain the context retrieval and augmentation process in a RAG pipeline. Describe how retrieved documents are integrated into the prompt sent to the LLM.

After the knowledge base has been prepared, every user query goes through retrieval (find relevant chunks) and augmentation (put them into the prompt) before the LLM generates the answer.

Context retrieval

  1. Embed the query with the same model that embedded the chunks.
  2. Similarity search in the vector database for the top-\(k\) chunks (Q33, Q34).
  3. Filter with metadata (source, date, user access rights) and a similarity threshold \(s\ge\tau\) so weak matches are dropped.
  4. Refine (optional): remove near-duplicates and re-rank (Q38).

Context augmentation

The selected chunks are combined with the question and instructions into one prompt: Augmented prompt = Instructions + Retrieved context + User query.

You are a helpful assistant. Answer ONLY using the context below.
If the answer is not in the context, say "I don't know". Cite the source id.

Context:
[1] (handbook.pdf, p.12) "Students must have at least 75% attendance ..."
[2] (handbook.pdf, p.13) "Condonation up to 65% is allowed with medical proof ..."

Question: What is the minimum attendance to appear for the semester exam?

Fitting the context window

The chunks must fit the model's window \(N\) together with everything else (Q26): choose the largest \(k\) such that

\[n_{\text{instr}}+\sum_{i=1}^{k}n(c_i)+n_{\text{query}}+n_{\text{answer}}\ \le\ N\]

Strategies when there is more context than fits

StrategyHow
StuffingPut all top-\(k\) chunks into one prompt (simplest, used when they fit)
Map-reduceAnswer or summarise each chunk separately, then combine the partial results
RefineProcess chunks one by one, improving the answer each time

Practical points

  • Order: put the most relevant chunks first (or at the ends), since models under-use the middle of long contexts.
  • Grounding instruction: tell the model to rely only on the context and to say when the answer is missing; ask for citations.
  • Risks: irrelevant or contradictory chunks, and untrusted documents that contain hidden instructions (prompt injection), so retrieved text should be treated as data, not as commands.

37. Discuss hybrid retrieval techniques that combine dense (embedding-based) and sparse (keyword-based) retrieval methods. Explain the advantages of hybrid retrieval over using either method alone.

Hybrid retrieval combines sparse (keyword) and dense (embedding) retrieval and merges their results, so that the system gets both exact matches and semantic matches.

Sparse retrieval — BM25

Scores documents by the query words they contain, weighting rare words more (IDF) and normalising for term frequency and document length:

\[\mathrm{BM25}(q,d)=\sum_{t\in q}\mathrm{IDF}(t)\cdot\frac{f(t,d)\,(k_1+1)}{f(t,d)+k_1\left(1-b+b\,\frac{|d|}{\mathrm{avgdl}}\right)}\]

Good at exact terms: names, error codes, IDs, rare technical words. Fails when the query uses different words from the document.

Dense retrieval

Ranks by embedding similarity, \(\cos(e_q,e_d)\) (Q33). It captures meaning and paraphrases (“page not found” matches “404 error”) but can miss exact identifiers and rare terms.

Combining the two

  • Weighted score fusion: normalise both scores to [0,1] and compute
    \[s(d)=\alpha\,\hat s_{dense}(d)+(1-\alpha)\,\hat s_{sparse}(d)\]
  • Reciprocal Rank Fusion (RRF): uses only ranks, so no score normalisation is needed (typically \(k=60\)):
    \[\mathrm{RRF}(d)=\sum_{r\in\text{rankers}}\frac{1}{k+\mathrm{rank}_r(d)}\]

Worked example (RRF, \(k=60\))

DocumentDense rankBM25 rankRRF score
A13\(\frac1{61}+\frac1{63}=0.03227\)
B21\(\frac1{62}+\frac1{61}=0.03252\)
C32\(\frac1{63}+\frac1{62}=0.03200\)

Final order: B, A, C. B wins because it is ranked high by both retrievers, even though A is first for dense retrieval alone.

Advantages of hybrid over either alone

Sparse onlyDense onlyHybrid
Exact terms, IDs, codesStrongWeakStrong
Paraphrase and meaningWeakStrongStrong
Rare or out-of-vocabulary wordsStrongCan missStrong
Robustness across query typesLowMediumHigh
CostCheap, no modelNeeds embeddings + vector indexBoth (modest extra cost)

Hybrid retrieval is usually followed by a re-ranker (Q38) and is the default in many production RAG systems.

38. Explain query expansion and re-ranking techniques used to improve the accuracy of retrieval in RAG systems. Illustrate with an example how re-ranking modifies the final set of retrieved documents.

The Retrieval Problem

User queries are often short, vague or worded differently from the documents ("vocabulary mismatch"), and first-pass vector search is fast but approximate. Two techniques improve accuracy: expand the query before retrieval and re-rank results after retrieval.

User Query → Query Expansion → Retrieve Top-N (fast) → Re-rank (accurate) → Top-k to LLM

Query Expansion Techniques

TechniqueHow it works
Synonym / thesaurus expansionAdd synonyms and related terms ("car" → "automobile, vehicle")
LLM-based rewritingLLM rewrites the query to be clearer and more complete; also resolves chat context ("What about its price?" → "What is the price of Product X?")
Multi-query generationLLM produces several paraphrases; retrieve for each and merge results — improves recall
HyDE (Hypothetical Document Embeddings)LLM writes a hypothetical answer; its embedding (closer to real documents than the short query) is used for search
Pseudo-relevance feedbackTake top initial results, extract key terms, add them to the query and search again
Step-back / decompositionBreak a complex question into sub-questions, or ask a more general version first

Effect: increases recall — more of the truly relevant documents are present in the candidate set.

Re-ranking Techniques

First-stage retrieval uses a bi-encoder: query and document are embedded independently, so similarity is a cheap dot product but loses fine-grained interaction. A re-ranker then rescores only the top-N candidates (e.g., 50) more carefully.

Re-rankerDescription
Cross-encoderFeeds query and document together through a transformer (BERT/MiniLM) which outputs a relevance score — much more accurate but slower
LLM-based re-rankingAsk an LLM to score or order passages by relevance
Cohere Rerank / BGE-rerankerHosted/open-source ready-made rerankers
Reciprocal Rank Fusion (RRF)Merges rankings from multiple retrievers (keyword + vector)
MMRMaximal Marginal Relevance — balances relevance and diversity to avoid near-duplicates
\[ \text{RRF}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)} \qquad\qquad \text{MMR} = \arg\max_{d_i \in C\setminus S}\Big[\lambda\,\text{sim}(d_i,q) - (1-\lambda)\max_{d_j\in S}\text{sim}(d_i,d_j)\Big] \]

Example: How Re-ranking Changes the Result

Query: "How can I reset my password if I no longer have access to my registered email?"

DocContent (summary)Stage-1 rank (cosine)Re-ranker scoreFinal rank
D1"How to reset your password using your registered email"1 (0.89)0.453
D2"Password policy: length and character requirements"2 (0.84)0.125
D3"Account recovery without email: identity verification via support"4 (0.78)0.961
D4"Recover account using registered phone number OTP"3 (0.80)0.812
D5"Change email address in profile settings"5 (0.74)0.304

What changed: The bi-encoder ranked D1 first because it shares many words with the query ("reset password registered email"). The cross-encoder, reading query and document together, understood the key constraint — no access to email — and promoted D3 and D4 (the truly useful answers) to the top, demoting D1 and D2. Final context sent to the LLM: D3, D4, D1 (top-3).

Conclusion: Query expansion widens the net (recall); re-ranking sharpens the catch (precision). Together they ensure the LLM receives the most relevant context, directly improving answer accuracy.

39. Discuss the evaluation of RAG systems. Explain key evaluation metrics such as faithfulness, answer relevance, and context precision/recall, and describe how they are measured.

A RAG system has two parts that can fail independently, so it is evaluated in two layers: retrieval quality (did we fetch the right evidence?) and generation quality (did the LLM use it correctly?). The three relationships between query, context and answer are often called the RAG triad.

Retrieval metrics

MetricDefinition
Precision@k\(\dfrac{\#\text{relevant chunks in top-}k}{k}\)
Recall@k\(\dfrac{\#\text{relevant chunks in top-}k}{\#\text{relevant chunks that exist}}\)
MRR\(\dfrac1{|Q|}\sum_{q}\dfrac1{\mathrm{rank}_q}\), where rank is the position of the first relevant chunk
Context precisionAre the relevant chunks ranked at the top? Mean of precision@\(i\) over the positions \(i\) of relevant chunks (rank-aware).
Context recall\(\dfrac{\#\text{statements of the reference answer supported by the context}}{\#\text{statements in the reference answer}}\): was all needed evidence retrieved?

Generation metrics

MetricDefinition and how it is measured
Faithfulness (groundedness)\(\dfrac{\#\text{claims in the answer supported by the retrieved context}}{\#\text{claims in the answer}}\). An LLM judge splits the answer into claims and checks each against the context. Low faithfulness = hallucination.
Answer relevanceDoes the answer address the question? Often measured by generating questions back from the answer and averaging their embedding similarity with the original question.
Answer correctnessAgreement with a reference answer (exact match, F1, or LLM judge).

Worked example

For one query the retriever returns 5 chunks and chunks 1 and 3 are relevant; the corpus has 4 relevant chunks in total.

\[P@5=\frac25=0.4,\qquad R@5=\frac24=0.5,\qquad \text{context precision}=\frac{1/1+2/3}{2}=0.83\]

The generated answer makes 5 claims and 4 are supported by the context, so faithfulness \(=4/5=0.8\).

How evaluation is done

  • Build a test set of questions with reference answers and, where possible, the supporting passages.
  • Use an LLM-as-a-judge for faithfulness and relevance, complemented by human review of samples.
  • Tools such as RAGAS, TruLens and DeepEval compute these metrics automatically.
  • Also track latency, cost per query and user feedback in production (Q47).

Diagnosis: low context recall → fix chunking, embeddings or retrieval; low faithfulness → fix the prompt or the model; low answer relevance → fix query handling and the prompt.

40. Design a RAG-based solution for an enterprise use case such as knowledge management, a research assistant, or a customer support system. Justify the design choices for embedding model, vector database, and retrieval strategy.

Chosen Use Case: Enterprise Customer-Support Assistant

Goal: A chatbot that answers customer and agent questions using the company's product manuals, FAQs, past tickets and policy documents — accurately, with citations, and with access control.

System Architecture

Sizing the system (worked estimate)

Suppose 50,000 documents of about 20 chunks each, i.e. \(10^6\) chunks, embedded with a 1,024-dimension model in float32:

\[10^6\times1024\times4\ \text{bytes}\approx4.1\ \text{GB of raw vectors}\]

With HNSW graph overhead this is roughly 6 GB, comfortably in RAM on a single server; product quantisation could shrink it ~30× if the corpus grows to hundreds of millions of chunks (Q34).

Latency budget for one answer

StepTarget
Query embedding~20 ms
Vector + keyword search with filters~50 ms
Reranking top-50 to top-5~150 ms
LLM generation (streamed)first token in ~1 s

Streaming the answer keeps the interface responsive even when the full generation takes a few seconds.

Safety, evaluation and operations

  • Access control: filter retrieval by the user's role so the model never sees documents the user may not read.
  • Fallback: if the best retrieval score is below a threshold, answer “I could not find this” or hand over to a human instead of guessing.
  • Evaluation: a fixed test set of real questions, tracking Recall@k, faithfulness and answer relevance (Q39), re-run after every change.
  • Monitoring and feedback: thumbs up/down, deflection rate, unanswered queries and stale documents feed the next improvement cycle (Q47).

Choice: Qdrant / Weaviate (or pgvector if already on PostgreSQL) — supports metadata filtering (product, version, language, access role), hybrid search, HNSW indexing for low latency, horizontal scaling, and on-premise deployment for compliance.

3. Retrieval Strategy

  • Hybrid search = dense vectors + BM25 keyword, fused by RRF — vectors capture meaning, BM25 catches exact error codes and product IDs.
  • Query rewriting using chat history to resolve follow-up questions.
  • Metadata / ACL filters so users only retrieve documents they are authorised to see.
  • Two-stage retrieval: fetch Top-20 quickly, cross-encoder re-rank to Top-5.
  • Parent-child chunks: match on small chunks, send larger parent section to the LLM.
  • Grounded prompt: "Answer only from the context; cite sources; say 'I don't know' otherwise."
